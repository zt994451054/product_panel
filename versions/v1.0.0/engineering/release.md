# v1.0.0 发布流程

> 数据库变更见 [db-design.md](./db-design.md)（含增量 DDL 和回滚 DDL）；发布可行性见 [tech-solution.md](./tech-solution.md)「发布可行性」
> 测试通过确认见 [../testing/test-report.md](../testing/test-report.md)
> 本项目实际怎么构建、部署、回滚、验证，以 [运维与发布画像](../../../engineering/docs/ops-profile.md) 为准；本文件只写本版本要执行的具体步骤，命令、窗口、审批都按画像填写，不照搬示例。

> 四段：发布前提 → 执行 → 生产业务验证 → 发布记录。收尾在版本交付签收后按 SOP-07「→ 已发布」清单做。

## 一、发布前提

> 全部满足后才能开始执行；任一未满足就暂停，告诉使用者缺什么。每条写明依据（谁确认的、在哪里能看到）。

- [ ] 测试报告结论为「通过」，测试阶段已由使用者签收
- [ ] 全部缺陷已关闭，未关闭的都有使用者逐条豁免（test-report.md「豁免登记」）
- [ ] **发布制品就是测过的制品**：本次要发的制品（镜像、包、构建号）与 test-report.md「被测构建」一致；不一致时说明差异，受影响用例已重测
- [ ] **生产结构已核对**：tech-solution.md「发布可行性」的生产结构比对在发布前重新只读核对一次，与当时一致
- [ ] **发布与回滚演练**（有数据库结构变更、数据迁移、不可逆的配置或基础设施变更时必须做；纯代码变更写「不需要：回滚方式为重新部署上一个制品」）：在与生产结构一致的库或环境上，用实际发布的方式执行一次发布和回滚，记录在下方「演练记录」

- [ ] 回滚方案已写好（本文件「回滚方案」）
- [ ] 代码已合并至发布分支，流水线通过

## 三、生产业务验证

> 健康检查通过只说明进程活着。部署后必须对本版本影响到的每条业务路径，在生产上发一次真实的业务请求并留证据；全部通过才算发布成功，之后进入生产验收（SOP-12）。
> 写操作（造单、建账号）先取得使用者同意，验证后按约定清理；验证方式和账号以 ops-profile.md「生产验证方式」为准。
