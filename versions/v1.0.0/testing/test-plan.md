### 回归测试范围

> 本版本变更可能影响的已有功能，需要执行回归验证。每一行都要在 test-cases.md 中有对应的回归用例。
> **怎么推出范围**（不凭感觉，也不默认全量）：
> 1. 改了什么：从 tech-solution / api-design / db-design 和代码差异中列出改动的模块、接口、表、公共组件
> 2. 谁依赖它：查调用方、引用方、读这张表的地方、用这个组件的页面
> 3. 落到功能：把第 2 步找到的地方对应到已有功能或用户流程，每个功能一行
> 4. 裁剪要确认：第 3 步列出的功能决定不回归的，写明理由，由使用者逐条同意（记入 decisions.md）

> 测试设计阶段填写，「→ 测试」门控逐行核对。目的是在执行前就发现环境、设备、账号、需人在场等阻塞，不要到执行时才暴露。

| 用例范围 | 需要的环境 | 设备 / 终端 / 第三方版本 | 账号与数据 | 需要人在场的步骤 | AI 能否独立执行 | 就绪状态 |
|---------|----------|---------------------|----------|---------------|---------------|---------|
| <!-- TC-001~010（Web 预约） --> | <!-- staging --> | <!-- Chrome 最新版 --> | <!-- 测试账号 A、B；时段种子数据 --> | <!-- 无 / 短信验证码、扫码、真机、生产操作 --> | <!-- 是 / 否（原因） --> | <!-- ✅ 就绪 / ⏳ 未就绪（缺什么、谁负责） --> |

> 需要人在场的步骤，执行时 AI 做到这一步就停，告诉使用者需要做什么；无人值守时按 [collaboration.md](../../../agents/collaboration.md) §3 处理。

## 测试数据

> 测试数据是台账：建了什么、在哪、谁在用、怎么清，都记在这里。退出条件要求全部清理，或写明保留原因。
> 准备和校验方式按项目实际填写（调接口、直连测试库、跑脚本都可以），与 `testing/docs/environments.md` 一致即可。

| 数据 | 所在环境 / 位置 | 创建方式 | 使用的用例 | 清理方式 | 清理状态 |
|------|---------------|---------|----------|---------|---------|
| <!-- 测试账号 A（13800000001） --> | <!-- staging users 表 --> | <!-- 调注册接口 --> | <!-- TC-001~010 --> | <!-- 删除脚本 / 保留（原因） --> | <!-- ⏳ 未清理 / ✅ 已清理 / 保留 --> |

> ⚠️ 禁止在测试环境使用真实用户数据
> 本地执行用例时，数据按 `engineering/docs/local-env.md` §4 的隔离约定（个人 schema、key 前缀）写入；在共享测试环境（如 staging）执行时，用专用测试账号和可识别的数据前缀，便于清理。

## 进入条件

> 以下条件全部满足后，方可开始正式测试。每条勾选时在后面写明依据（谁确认的、在哪里能看到），须在进入测试时核对，**不得事后用执行结果反推勾选**。

- [ ] 本版本所有测试范围内的功能需求状态已更新为「已确认」（见 requirements.md）
- [ ] 本版本所有功能已开发完成并部署至 staging 环境
- [ ] 数据库变更（db-design.md 增量 DDL）已在 staging 环境执行
- [ ] 配置变更（tech-solution.md 配置变更需求）已在 staging 环境生效
- [ ] 研发单元测试通过（CI 流水线绿色）
- [ ] 测试环境配置已与「生产默认配置」节核对，差异已按该节处理
- [ ] API 设计文档（api-design.md）已与实现核对一致
- [ ] 「执行就绪」表每行为 ✅ 就绪；未就绪的行，使用者已决定怎么处理（等就绪 / 逐条豁免相关用例）
- [ ] 已核对测试环境运行的是目标构建（提交号或构建号：____；核对方式：版本接口 / 构建号 / 进程，只看端口不算），记入 test-report.md「基本信息」

## 退出条件（测试通过标准）

| 条件 | 标准 |
|------|------|
| 用例覆盖 | test-cases.md 覆盖矩阵无空行：全部新特性点和改动点都有用例 |
| 用例执行 | 全部用例（P0/P1/P2/P3）已执行 |
| 用例通过 | 全部用例通过；未通过的用例只能由使用者逐条豁免，并登记在 test-report.md「豁免登记」 |
| 缺陷 | 全部缺陷（任何级别）关闭；未关闭的缺陷只能由使用者逐条豁免，并登记在 test-report.md「豁免登记」 |
| 原型还原 | 还原检查用例全部通过（还原优先级以 design-spec.md 为准，不得在测试阶段下调） |
| 生产默认配置 | P0 主流程用例确实按「生产默认配置」节的取值执行 |
| 回归测试 | 回归测试范围内每项已有功能的回归用例全部通过 |
| 性能测试 | 如 requirements.md 有性能要求，接口响应时间达标率 ≥ 99%；无性能要求则此条不适用 |
| 被测构建 | 全部通过结果对应最终被测构建；中途重新部署过的，受影响用例已重测，未重测的写明仍然有效的理由 |
| 人工干预 | defects.md「执行中的人工干预」每条都已判定是否产品缺陷 |
| 代码检查与自动化测试 | 本版本改动引入的问题为 0；历史存量问题数不增加（基数：____，来源：CI 报告 / 静态检查报告） |
| 测试数据 | 「测试数据」台账全部已清理，或写明保留原因 |
| 测试报告 | 已完成，结论为「通过」或「不通过」（没有「条件通过」） |

> 退出条件不得放宽。AI 不能替使用者豁免；使用者答复「你决定」「都行」视为未豁免（[SOP-03](../../../agents/sop/SOP-03-testing.md) 豁免规则）。

## 风险与应对

| 风险 | 可能影响 | 应对方案 |
|------|---------|---------|
| 外部依赖（如短信网关）在 staging 不可用 | 验证码相关用例无法正常执行 | 使用 mock 短信网关，在代码层 stub 短信发送 |
| staging 环境不稳定 | 测试结果不可信 | 发现环境问题及时上报，等待修复后重新执行 |
