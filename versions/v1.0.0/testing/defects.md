## 缺陷状态

缺陷的状态不写在本文档里。每个缺陷用 `node tools/panel.mjs defect open` 登记，拿到编号；之后每次状态变化都用命令记录，用 `defect list --version {版本}` 查看。本文档只写叙述：复现步骤、期望与实际结果、修复历程、证据。

```
待修复 → 修复中 → 已修复待复测 → 待验收 → 已关闭
            复测或验收不通过 → 退回「待修复」
已豁免（任何级别，只能由使用者逐条明示；AI 不得自行豁免）
```

| 状态 | 说明 | 命令 |
|------|------|------|
| 待修复 | 缺陷已登记，等待修复 | `defect open` |
| 修复中 | 正在修复 | `defect status --to fixing` |
| 已修复待复测 | 修复已完成，等重新执行关联用例 | `defect status --to fixed --build {构建}` |
| 待验收 | 复测通过，等人验收 | `defect status --to verifying` |
| 已关闭 | 人验收合格 | `defect close --verifier {成员} --quote "{原话}"` |
| 退回 | 复测或验收不通过，回到待修复 | `defect status --to open --note "{原因}"` |
| 已豁免 | 使用者逐条明示豁免（任何级别），同时记入 test-report.md「豁免登记」（测试阶段）或 decisions.md 和 acceptance.md「遗留问题说明」（生产业务验证、生产验收阶段）；P0 缺陷豁免前 AI 须向使用者说明风险 | `defect waive --scope --quote --by {成员}` |

## 说明

- **新增缺陷**：运行 `defect open` 登记并拿到编号，详情区用这个编号追加章节；关联用例在 test-cases.md「用例总览」改为 ❌ 失败
- **修复更新**（AI）：在「修复历程」节追加记录，运行 `defect status --to fixed`；复测通过后 `--to verifying`；填「是否改变原有约定」
- **验收更新**（人工）：使用者验收后，用 `defect close` 记录验收人和原话
- **关闭前**：「是否改变原有约定」为「是」的，回写完成才能关闭
- **工件上传**：截图/录屏/日志按 SOP-10 上传 OSS（路径 `versions/{ver}/testing/`，命名 `YYYYMMDD-BUG{序号}-描述.ext`，见 OSS.md），CDN URL 填入「工件 URL」字段
- **hotfix 场景**：已发布版本的生产缺陷记在 `foundation/product/production-bugs.md`（PROD 编号），不改已发布版本的本文件；热修复版本自己的 defects.md 只记它在测试和发布中发现的缺陷（SOP-11）
- **豁免**：任何级别的缺陷都只能由使用者逐条豁免；未豁免的缺陷必须本版本关闭，测试才能放行
- **原型还原偏差**：与原型不一致即记为缺陷，不得自行认定为「视觉小问题」而不记录
- **修复影响接口/DB/需求**：推进到「已发布」时按[全量基线与版本增量](../../../agents/baselines.md)合入基线（SOP-07 / SOP-11）
- 变更追踪 → [CHANGES.md](../CHANGES.md)
