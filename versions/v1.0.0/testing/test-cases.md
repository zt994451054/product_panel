## 用例登记与状态

> 每条用例先用命令登记拿到编号，再在下面「用例详情」写内容：
> `node tools/panel.mjs case add --version {ver} --title "…" --priority P0 --type api --items FEAT-xiaolin-001 --by ai`
> 编号由命令分配（TC-{成员标识}-{三位序号}）。`--items` 写它测的需求条目（必须已确认）；不对应任何需求条目的（兼容性、性能、回归已有功能）不写 `--items`，用 `--note` 说明测的是什么。
>
> **状态不写在这份文档里。** 每执行一次用 `case result` 记一次（结果、实际看到了什么、被测构建），查看用 `case list`，驾驶舱的版本详情页也有。
> - 状态：未执行 / 通过 / 失败 / 阻塞 / 需回归 / 已豁免
> - **阻塞**：预期依赖还没答复的问题（Q-{成员标识}-xxx），或执行就绪条件不满足，记阻塞并在 `--actual` 写原因，不记通过。依赖使用者逐条同意的暂定值（D-{成员标识}-xxx）可以记通过，在 `--actual` 注明「依据暂定值 D-{成员标识}-xxx」，暂定值变了用 `case regress` 退回需回归
> - **需回归**：需求条目变更（`item change`）、关联缺陷修复（`defect status --to fixed`）后，命令自动把相关用例退回需回归；重新部署等其他情况用 `case regress` 手工标
> - **已豁免**：只有使用者能逐条豁免，用 `case waive` 记录范围和他的原话
> - 测试类型：`ui` UI交互 / `ui_restore` UI还原 / `backend` 后端 / `api` 接口 / `e2e` E2E / `manual` 手工

## 说明

- **新增用例**：先 `case add` 登记，再同步 ①「覆盖矩阵」②「用例详情」；类型、优先级和登记时一致
- **只按实际执行结果记录**：没有实际执行的不记；使用者概括说「基本都过了」时，只记他明确点到的用例（一次一条，带他针对这条的原话 `--quote`，`--by` 写他）
- **重新部署后**：按改动判断哪些已通过的用例受影响，受影响的用 `case regress` 退回需回归；不受影响的不用动
- **失败附件**：失败截图、录屏按 SOP-10 上传 OSS（路径 `versions/{ver}/testing/`，命名 `YYYYMMDD-TC{序号}-描述.ext`，见 OSS.md），地址写进 `case result --actual`
- **需求变更**（SOP-04）后：`item change` 会把关联的已通过用例自动退回需回归。需求变了，原来的结果可能失效，不重测等于伪装通过
- 变更追踪 → `change list` 和 [CHANGES.md](../CHANGES.md)
