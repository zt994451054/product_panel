# 用例设计规范

> **主标准**：[ISTQB Certified Tester Foundation Level](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/)（通用测试设计技术）

> **说明**：本页讲用例怎么写好。测试设计与执行的流程、门控、评审和豁免规则见 [AGENTS.md](../../AGENTS.md) SOP-03，用例记录在 `versions/{ver}/testing/test-cases.md`。

---

## 用例依据

用例依据需求和技术方案设计，覆盖本版本全部新特性点，以及对现有功能逻辑和 UI 的全部改动点。

| 来源 | 从中提取什么 |
|------|-----------|
| `product/requirements.md` | 每条验收标准、非功能需求（新特性点）|
| `product/design-spec.md` | 每个用户流程和异常分支、原型页面映射表 |
| `engineering/tech-solution.md`、`api-design.md`、`db-design.md` | 对已有功能逻辑、接口、数据结构、UI 的每处改动（改动点）|
| `CHANGES.md` | 本版本已登记的变更 |
| `testing/test-plan.md` | 回归测试范围、生产默认配置 |

依据有缺口时（如某个异常分支没有定义）按 SOP-03 记入 requirements.md「待确认问题」，不要自己猜一个行为写进用例。

## 覆盖矩阵怎么建

先列项，再写用例。把上面的来源逐份过一遍，每一项在 `test-cases.md`「覆盖矩阵」占一行：

| 来源 | 特性点 / 改动点 | 覆盖用例 |
|------|---------------|---------|
| requirements.md #昵称 验收标准 1 | 昵称合法 → 保存成功 | TC-001 |
| design-spec.md 修改昵称流程 异常分支 | 昵称已被占用 | TC-002 |
| 原型 /web/profile（高保真）| 资料页还原 | TC-003 |
| tech-solution.md 用户接口新增 nickname 字段 | 回归：已有的用户详情查询 | TC-004 |

- **一行一项**：一条验收标准、一个异常分支、一个页面、一处改动各占一行，不要合并成「注册相关」这样的大行。
- **多对多**：一条用例可以覆盖多行，一行也可以由多条用例覆盖。
- **反向检查**：每条用例都应能回到矩阵的某一行。回不去的，要么矩阵漏列，要么用例多余。

## 用例粒度与标题

- 一条用例验证一个行为。不同分支拆成不同用例，失败时才能直接定位。
- 只有数据不同、步骤相同的场景，可以写成一条用例，测试数据列成表，每组数据写明各自的预期结果；任何一组不符合，整条用例判失败。
- 标题写「动词 + 对象 + 条件」，读标题就知道场景和预期。

| 合格 | 不合格 |
|------|-------|
| 昵称已被占用时保存应提示昵称已存在 | 昵称测试 |
| 未登录访问资料页应跳转登录页 | 测试 1 |

优先级：P0 阻断发布 / P1 严重影响功能 / P2 一般 / P3 轻微。优先级决定执行顺序，不决定用例能否不通过。

## 四要素写到什么程度

判断标准：没参与编写的人照着做，不需要猜，也不需要问。

| 要素 | 写到什么程度 | 不合格 | 合格 |
|------|-----------|-------|------|
| **前置条件** | 环境、账号及其状态、配置项及取值、被测服务版本 | 用户已登录 | staging，被测版本 v1.2.0；账号 test01 已登录，昵称为 Alice；生产默认配置 |
| **操作步骤** | 具体到页面路径、控件、输入内容 | 修改昵称并保存 | 1. 打开 /web/profile 2. 点「编辑」 3. 昵称输入 Bob 4. 点「保存」 |
| **测试数据** | 具体值；需要准备的数据写明来源 | 任意有效昵称 | 昵称 Bob（2–20 字符，未被占用）|
| **预期结果** | 具体文案、数值、状态码、跳转、数据变化，见下节 | 保存成功 | 提示「保存成功」；页面昵称显示 Bob；`users.nickname` = Bob |

- 测试数据用专属账号和数据，执行前准备、执行后清理，保证可重复执行，不污染业务数据。
- 「整体验证点」写终态校验（落库、缓存、下游消息）。接口返回 200 但数据没落库时，步骤通过，用例仍然失败。

## 预期结果：只有一种正确结果

判断标准：两个人分别执行，看到同一个现象，一定给出同一个判定。

| 禁用写法 | 问题 | 改写示例 |
|---------|------|---------|
| 显示正常 | 没说显示什么 | 列表按创建时间倒序显示 3 条记录，第一条标题为「订单 A」 |
| 符合预期 | 预期没有写出来 | 写出具体结果，如余额从 100.00 变为 80.00 |
| 功能可用 | 无法判定 | 点「导出」后下载 `orders.csv`，含表头和 3 行数据 |
| 提示错误信息 | 文案不确定 | 输入框标红，提示「昵称已存在」，停留在当前页 |
| 返回 4xx | 多种结果都算对 | 返回 HTTP 409，错误码 `NICKNAME_TAKEN` |
| 401 或 403 | 两种结果都算对 | 未登录返回 HTTP 401，错误码 `UNAUTHENTICATED` |
| 响应很快 | 没有判定值 | P99 < 500ms（目标值取自 test-plan.md「非功能需求测试目标」）|

- **文档没写明的，先补文档或提问**。比如 api-design.md 只写了「参数错误返回 4xx」：先把具体状态码和错误码补进 api-design.md，或按 SOP-03 提问，再写用例。不要在用例里留范围，也不要照着实现的行为反写预期。
- **动态值写判定规则**。订单号、时间戳这类每次不同的值，写成确定的规则：`orderId` 非空，且与 `orders` 表新增记录的 `id` 相同。
- **非功能目标写成阈值**。「P99 < 500ms」判定结果只有达标和未达标，属于可判定的预期。

## 异常分支和边界值设计方法

design-spec.md 用户流程里的每个分支都要有用例。下面的方法用来找出文档没逐条列出的取值和组合，示例都以「昵称长度 2–20 字符」这类通用规则为例。

### 等价类划分

把输入分成行为相同的若干类，每类取一个代表值，有效类和无效类都要有。

| 类别 | 代表值 | 预期结果 |
|------|-------|---------|
| 有效：长度在范围内 | Alice（5 字符）| 提示「保存成功」，`users.nickname` = Alice |
| 无效：长度过短 | A（1 字符）| 提示「昵称长度须为 2–20 个字符」，未保存 |
| 无效：长度过长 | 21 个字符 | 提示同上，未保存 |
| 无效：为空 | 空字符串 | 提示「请输入昵称」，未保存 |

### 边界值分析

缺陷常出在边界上。在有序范围的每条边界上，取边界值和紧邻的无效值：

| 昵称长度 | 预期结果 |
|---------|---------|
| 1（无效）| 提示「昵称长度须为 2–20 个字符」，未保存 |
| 2（边界）| 提示「保存成功」，昵称已更新 |
| 20（边界）| 提示「保存成功」，昵称已更新 |
| 21（无效）| 提示「昵称长度须为 2–20 个字符」，未保存 |

金额、数量、日期、分页大小都按此取值。没有上限的字段也要问清上限，文档没写就先补文档。

### 判定表

多个条件组合决定结果时，列出组合，每列一条用例。例：满减券使用规则。

| 条件 / 结果 | 组合 1 | 组合 2 | 组合 3 | 组合 4 |
|-----------|-------|-------|-------|-------|
| 订单金额达到门槛 | 是 | 是 | 否 | 否 |
| 券在有效期内 | 是 | 否 | 是 | 否 |
| 结果 | 实付金额减去券面额 | 提示「优惠券已过期」 | 提示「未达到使用门槛」 | 提示「优惠券已过期」 |

组合 4 这类两个条件同时不满足的情况，提示哪一条必须由文档写明，否则记为待确认问题。

### 状态迁移

对象有状态时，先画出状态和迁移，再覆盖每条有效迁移，并挑出关键的无效迁移。例：`待支付 → 已支付 → 已发货 → 已完成`，`待支付 → 已取消`。

| 类型 | 当前状态 | 操作 | 预期结果 |
|------|--------|------|---------|
| 有效 | 待支付 | 支付 | 状态变为已支付 |
| 有效 | 待支付 | 取消 | 状态变为已取消 |
| 无效 | 已取消 | 支付 | 返回错误码 `ORDER_CANCELLED`，状态仍为已取消，未扣款 |
| 无效 | 已完成 | 取消 | 返回错误码 `ORDER_COMPLETED`，状态仍为已完成 |

### 常见异常清单

写完上面的用例后，再按这份清单补漏：

- **输入**：空值、null、超长、特殊字符、格式错误、类型错误
- **权限**：未登录、登录过期、无权限、访问他人数据
- **操作**：重复提交、并发修改、中途取消、返回后重新进入
- **依赖**：第三方超时或失败、网络中断、资源不存在、存量数据缺字段

## UI 还原用例

- 测试类型选「UI还原」，「原型对照」写原型路由、还原优先级、原型基准，如：`/web/register，高保真，基准 a1b2c3d`。三项都取自 design-spec.md「原型增量」。
- 对照的是基准提交那一版原型，不是原型的最新状态。
- 预期结果逐项写对照要点，不写「与原型一致」一句话带过。各还原优先级的要求见[原型 README](../../foundation/design/prototype/README.md)「还原优先级」，视觉取值见 [DESIGN.md](../design/DESIGN.md)。

| 还原优先级 | 预期结果要写的对照项 |
|----------|-----------------|
| 高保真 | 布局、组件、文案、各状态（加载/空/错误/禁用）、交互逐项对照；间距、颜色按 DESIGN.md 取值 |
| 参考还原 | 视觉风格与 DESIGN.md 一致，细节布局可以不同；交互、流程、文案、状态仍逐项对照 |

还原优先级在产品设计阶段确定，用例不得下调；还原偏差记为缺陷。

## P0 按生产默认配置执行

- 先看 test-plan.md「生产默认配置」表，把影响结果的配置项和取值写进 P0 主流程用例的前置条件。
- 测试环境与生产默认值不一致的，按该表写明的差异处理方式执行（如 P0 用例执行前改为生产值）。
- 为了测某个分支而调整配置的（如缩短有效期来测过期），写成单独的用例并在前置条件写明改动，不能代替 P0 主流程用例。
- 被替换的外部依赖（如用沙箱代替真实短信网关）也写进前置条件。

## 回归范围怎么定

从改动点出发，不凭感觉挑模块。对每处改动问三个问题：谁依赖它？它的行为变了吗？存量数据还能用吗？

| 改动类型 | 回归对象 |
|---------|---------|
| 接口字段或语义变化 | 该接口的所有调用方 |
| 表结构变化、数据迁移 | 读写该表的功能，以及存量数据 |
| 公共组件、样式变化 | 使用该组件的页面 |
| 权限或配置变化 | 受影响的角色、默认值生效的流程 |
| 公共函数、中间件变化 | 经过它的主要流程 |

- 结果写进 test-plan.md「回归测试范围」，每一行都写明受影响原因，并在覆盖矩阵中有回归用例。
- 判断不回归的已有功能，写进「排除测试」并说明理由。
- 回归用例同样四要素完整，预期写已有行为的具体结果，不写「不受影响」。
