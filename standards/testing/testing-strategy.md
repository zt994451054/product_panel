# 测试策略总览

> **主标准**：[Test Pyramid - Martin Fowler](https://martinfowler.com/articles/practical-test-pyramid.html)
> **副标准**：[Google Testing Blog](https://testing.googleblog.com/)、[DORA Metrics](https://dora.dev/)

---

## 测试金字塔（Test Pyramid）

Martin Fowler 提出的测试金字塔是行业公认的测试分层模型：

```
           ▲
          /E2E\          少量（5-10%）
         /─────\         慢、成本高、覆盖关键流程
        /集成测试\        适量（20-30%）
       /─────────\       中等速度、测试服务间协作
      /  单元测试  \      大量（60-70%）
     /─────────────\     快、廉价、覆盖业务逻辑
```

图中比例是经验参考，不作为要求。

**反模式——冰淇淋锥（Ice Cream Cone）：**

```
大量 E2E → 慢、脆弱、维护成本高、定位问题难
少量单元 → 业务逻辑缺乏保护
```

---

## 各层测试定义

| 层次 | 测试对象 | 速度 | 维护与执行时机 | 示例 |
|------|---------|------|-------------|------|
| **单元测试** | 单个函数/类/方法，隔离外部依赖 | 毫秒级 | 由研发编写，在工程仓库中维护 | 计算逻辑、数据校验 |
| **集成测试** | 多个组件协作，含真实 DB/MQ | 秒级 | 自动化，每次 CI 触发（没有 CI 时每次合入前运行）| Repository 层、消息消费者 |
| **API 测试** | HTTP 接口（黑盒）| 秒级 | 同集成测试 | 下单接口、登录接口 |
| **E2E 测试** | 完整用户流程（含 UI）| 分钟级 | 在独立于生产的测试环境（如 staging）执行 | 注册→下单→支付流程 |
| **性能测试** | 吞吐量、延迟、稳定性 | 分钟-小时 | 压测/负载，版本发布前执行 | 压测核心接口 |

## 测试覆盖率要求

全模板只在这里定义覆盖率目标，其他页面引用本节。下表是默认值，项目可以修改：

| 层级 | 默认覆盖目标 |
|------|-----------|
| 单元测试 | 行覆盖率 ≥ 80%（整体和新增代码都按此计）|
| 集成测试 | 核心链路 100% |
| E2E 测试 | 主流程 100% |
| 性能测试 | 按版本定义，目标见[性能测试规范](performance-testing.md) |

工具库可以调高，脚手架和配置类可以调低，调整后写入本节。

**覆盖率不替代测试底线：** 代码覆盖率只说明代码被执行过多少。测试底线要求用例覆盖全部新特性点和对现有功能逻辑、UI 的全部改动点，并且全部用例执行通过（[AGENTS.md](../../AGENTS.md) SOP-03）。覆盖率达标也不能放行未满足底线的版本；覆盖率默认值可以改，测试底线不能放宽。

**覆盖率说明：**
- **行覆盖率（Line Coverage）** 是最低要求，不代表测试质量
- **分支覆盖率（Branch Coverage）** 更有价值，建议关注
- 覆盖率高不等于测试好：没有断言的测试毫无意义

## 测试环境策略

环境划分由项目自己定义，下表是一种常见做法，不是要求：

| 环境 | 用途 | 使用的外部依赖 |
|------|------|--------------|
| 本地开发 | 快速反馈，单元测试 | Mock / 本地 Docker |
| CI（自动化）| 拉取请求时运行 | 真实 DB（测试库）+ Mock 外部服务 |
| 测试环境 | 集成测试、E2E 测试 | 真实基础设施（测试数据）|
| 预发布环境 | 冒烟测试、性能测试 | 与生产配置相同 |

不论环境怎么划分：研发阶段的测试不操作生产数据；发布后的生产验收按 SOP-12 执行，只用指定的验收账号和数据；P0 主流程用例按生产默认配置执行（[AGENTS.md](../../AGENTS.md) SOP-03）。

**测试数据管理原则：**
- 单元测试：代码内构造测试数据，不依赖外部状态
- 集成测试：测试前初始化（Setup），测试后清理（Teardown）
- E2E 测试：使用专属测试账号，避免污染业务数据

## 何时写什么测试

| 场景 | 写什么测试 |
|------|----------|
| 业务逻辑（计算、校验、状态流转）| 单元测试（必须）|
| 数据库查询/ORM 操作 | 集成测试（真实 DB）|
| HTTP API 接口 | API 测试（Postman/REST Assured）|
| 消息队列消费者 | 集成测试（真实 MQ 或 TestContainer）|
| 关键用户流程 | E2E 测试（Selenium/Playwright）|
| 发布前性能验证 | 性能测试（k6/Gatling）|

## TDD（测试驱动开发）

推荐对复杂业务逻辑使用 TDD：

```
1. 写一个失败的测试（Red）
2. 写最少代码让测试通过（Green）
3. 重构代码，保持测试通过（Refactor）
```

**适合 TDD 的场景：** 业务规则复杂、边界情况多、需求明确
**不适合 TDD 的场景：** 探索性开发、UI 原型、基础设施配置

## 测试质量原则

**好测试的特征（F.I.R.S.T 原则）：**

| 原则 | 说明 |
|------|------|
| **F**ast（快速）| 单元测试应该在毫秒内完成 |
| **I**solated（隔离）| 测试不依赖其他测试的执行顺序和状态 |
| **R**epeatable（可重复）| 在任何环境运行，结果一致 |
| **S**elf-validating（自验证）| 自动判断通过/失败，不需要人工检查 |
| **T**imely（及时）| 与生产代码同步编写，不是事后补充 |

**禁止事项：**
- 【禁止】没有断言（assert）的测试
- 【禁止】测试之间共享可变状态
- 【禁止】单元测试依赖外部服务（数据库、网络、第三方 API），应 Mock
- 【禁止】集成测试依赖不可控的第三方服务或生产服务；数据库、消息队列用真实的测试实例（见[集成测试规范](integration-testing.md)）
- 【禁止】Skip 失败的测试来让流水线通过；要跳过只能由使用者逐条豁免（[AGENTS.md](../../AGENTS.md) SOP-03）

**用例底线：** 用例四要素必填、预期结果可直接判定、全部通过才放行。写法见[用例设计规范](test-case-design.md)，流程见 [AGENTS.md](../../AGENTS.md) SOP-03。

## 缺陷规范

- 严重级别：P0（阻断）/ P1（严重）/ P2（一般）/ P3（轻微）
- 缺陷状态流转：⏳ 待修复 → 🔄 修复中 → ✅ 已修复 → 🕐 待验收 → ✅ 验收通过 / ❌ 验收失败

---

## 发布门禁

- 全部用例执行并通过、全部缺陷关闭，才能推进到发布；未通过项只能由使用者逐条豁免并登记（[AGENTS.md](../../AGENTS.md) SOP-03 测试底线与豁免规则）
- 测试结论只有「通过」和「不通过」
- 具体退出条件见 `versions/{ver}/testing/test-plan.md`「退出条件」，各版本不得放宽
