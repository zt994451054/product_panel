# 需求管理规范

> **主标准**：[IEEE 29148:2018 - Systems and Software Engineering Requirements](https://standards.ieee.org/ieee/29148/6938/)
> **副标准**：[Agile Alliance - User Stories](https://www.agilealliance.org/glossary/user-stories/)、[Mike Cohn - User Stories Applied](https://www.mountaingoatsoft.com/books/user-stories-applied/)

---

## 需求的三个层次

| 层次 | 对应 | 描述 |
|------|------|------|
| **业务需求（Business Requirements）** | 为什么要做 | 业务目标、期望结果 |
| **用户需求（User Requirements）** | 用户要什么 | 用户故事、使用场景 |
| **系统需求（System Requirements）** | 系统做什么 | 功能需求 + 非功能需求 |

---

## 用户故事格式（Agile Alliance）

标准用户故事格式：

```
作为 <角色>，
我希望 <完成某件事>，
以便 <获得某种价值>。
```

**示例：**

```
作为首次购房的买家，
我希望能设置自定义的房源监控条件（区域 + 价格区间 + 房型），
以便在符合条件的房源上架后第一时间收到通知，不需要每天手动刷新。
```

**好用户故事的标准（INVEST 原则）：**

| 字母 | 含义 | 说明 |
|------|------|------|
| **I**ndependent | 独立 | 尽量减少故事间依赖，可单独排期 |
| **N**egotiable | 可协商 | 细节可以谈，不是固定契约 |
| **V**aluable | 有价值 | 对用户或业务有明确价值 |
| **E**stimable | 可估算 | 团队能估算工作量 |
| **S**mall | 适当小 | 一个迭代（或一个版本内的一个排期周期）内可完成 |
| **T**estable | 可测试 | 有明确的验收标准 |

## 需求拆分层级

```
Epic（史诗）：大型功能，跨多个迭代或版本
  └── Feature（特性）：可独立发布的功能
        └── User Story（用户故事）：一个迭代内完成
              └── Task（任务）：具体开发/设计任务
```

**拆分信号：**
- 用户故事超过 1 个迭代 → 需要拆分
- 用户故事包含 "以及"、"同时" → 可能有两个故事
- 验收条件超过 5 条 → 考虑拆分

## 需求优先级管理

面板的需求优先级使用 P0 / P1 / P2（定义见 [需求文档模板](../../versions/v1.0.0/product/requirements.md)），不在本规范之外另设一套。

### MoSCoW（可选方法）

团队习惯 MoSCoW 时，可作为讨论工具，并按下表映射为面板优先级：

| MoSCoW | 含义 | 比例参考 | 面板对应 |
|--------|------|---------|---------|
| **Must Have** | 必须有，没有不上线 | 工作量 ≤ 团队容量的 60%（留缓冲） | P0 |
| **Should Have** | 应该有，可以 delay | ≤ 20% | P1 |
| **Could Have** | 可以有，资源允许时做 | ≤ 20% | P2 |
| **Won't Have** | 本次不做（明确排除） | 无上限 | 边界说明（Out of Scope） |

【推荐】每个版本明确 P0（Must Have）范围，并为计划外工作留出缓冲

### 优先级排序依据

```
优先级 = f(用户价值, 业务价值, 实现成本, 风险)
```

常用排序框架：
- **RICE Score**：Reach（覆盖人数）× Impact（影响程度）× Confidence（置信度）/ Effort（工作量）
- **Kano Model**：基本型（必须有）/ 期望型（越多越好）/ 兴奋型（超预期）

## 需求生命周期

```
识别 → 分析 → 规格化 → 评审 → 基线化 → 实现 → 验证 → 维护
```

### 需求状态

面板已定义两套状态，本规范不再另设状态机：

| 层面 | 状态 | 定义位置 |
|------|------|---------|
| 需求池（跨版本，一行一个需求点） | 待评审 / 已确认 / 已纳入版本 / 已拒绝 / 已推迟 | `foundation/product/backlog.md`，操作流程见 SOP-00.5 |
| 版本需求文档（按模块） | 草稿 / 已确认 / 已变更 | `versions/{ver}/product/requirements.md`，需求状态为「已确认」后才能推进技术方案和测试用例 |

通用术语与面板状态的对照（便于阅读其他资料时理解）：

| 通用术语 | 面板对应 |
|---------|---------|
| Draft | 需求池「待评审」；需求文档「草稿」 |
| In Review / Approved | 需求池「已确认」；需求文档「已确认」 |
| In Progress / Done | 由版本阶段表示（开发中 / 测试），不在需求层面单独设状态 |
| Accepted | 版本验收按 SOP-12 签收，不单设需求状态 |
| Rejected / Deferred | 需求池「已拒绝」「已推迟」 |

## Backlog 管理规范

【必须】需求池的新增、评审、纳入版本按 SOP-00.5 执行，记录在 `foundation/product/backlog.md`

【推荐】需求池保持有序，最高优先级的需求靠前

【必须】需求进入开发前须满足（与「需求状态 = 已确认」一致）：
- 有明确的验收标准
- 依赖关系已明确
- 设计稿或原型已完成（UI 类需求）

【可选】团队按固定节奏（如每周一次、约 1 小时）梳理需求池，提前为后续一两个版本或迭代梳理好需求

## 需求变更管理

【必须】需求变更按 SOP-04 执行：先在 `versions/{ver}/CHANGES.md` 记录变更并列出影响范围，再修改文档，需求变更同时将模块状态改为「已变更」，并把关联的测试用例退回「需回归」

【必须】需求变更必须评估影响：范围变化 → 工期变化 → 资源变化

【可选】团队可以另行约定「迭代保护」，例如迭代进行中不接受新需求，必须变更时由使用者决策；该约定只能比 SOP-04 更严，不能跳过 CHANGES.md 记录
