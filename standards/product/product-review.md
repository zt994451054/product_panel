# 产品评审规范

> **主标准**：[Agile Alliance - Sprint Review](https://www.agilealliance.org/glossary/sprint-review/)
> **副标准**：[Shape Up（Basecamp）- Shipping](https://basecamp.com/shapeup/3.6-chapter-15)

---

## 评审类型

| 评审类型 | 时机 | 目的 | 参与方 |
|---------|------|------|--------|
| **需求评审** | 开发前 | 确认需求范围和细节，发现问题 | 产品 + 研发 + 测试 |
| **设计评审** | 设计稿完成后 | 确认 UI/UX 方案，对齐视觉和交互 | 产品 + 设计 + 研发 |
| **技术方案评审** | 开发前 | 确认实现方案，识别技术风险 | 研发 + 产品（可选）|
| **迭代评审（可选）** | 每个迭代结束 | 展示完成的功能，获取反馈 | 全团队 + 干系人 |
| **上线评审（可选）** | 发布前 | 最终确认发布范围和风险 | 产品 + 研发 + 运营 |

---

## 需求评审规范

### 评审前准备

【必须】需求方在评审前 **1 个工作日**发送以下材料：
- 需求文档（`versions/{ver}/product/requirements.md`）和设计说明（`design-spec.md`）
- 统一原型（`foundation/design/prototype/`）中对应页面的路由或链接
- 关键问题清单（已知的不确定点）

【必须】研发和测试在评审前阅读需求文档，提前准备问题

### 评审中

**评审关注点（按优先级）：**

1. **范围是否清晰**：Out of Scope 是否明确，边界是否有歧义
2. **需求是否可实现**：技术上是否可行，有无更好的实现方式
3. **验收标准是否完整**：能否判断"做完了"
4. **依赖是否明确**：第三方依赖、前置条件是否清晰
5. **非功能需求**：性能、安全、兼容性要求

**输出要求：**
- 评审结论：通过 / 需修改后复评（列出需修改项）/ 不通过
- 问题清单（待确认事项，指定负责人和 deadline），写入 requirements.md 的「待确认问题」节

## 设计评审规范

### 评审检查项

**功能层面：**
- [ ] 覆盖了需求文档中所有用例
- [ ] 空状态、加载状态、错误状态均有设计
- [ ] 边界情况（最长文本、最多列表项）已考虑

**体验层面：**
- [ ] 操作路径合理，核心任务的步骤尽量少（【推荐】经验值：核心任务不超过 3 步）
- [ ] 文案清晰，无歧义
- [ ] 本版本迭代的终端（见 requirements.md「本版本交互终端」）均已设计

**规范层面：**
- [ ] 与设计系统一致（颜色、字体、间距、组件）
- [ ] 符合 UI/UX 设计规范（可访问性、交互反馈）

## 迭代评审规范（可选）

团队按迭代（Sprint）节奏工作时，可在每个迭代结束时做迭代评审。面板按版本组织工作，不要求必须有迭代评审。

### 流程（时长参考：1-2 小时）

```
1. 回顾本迭代目标（5分钟）
2. 演示完成的功能（30-60分钟）
3. 干系人反馈（15-30分钟）
4. 更新需求池（10分钟，按 SOP-00.5）
5. 讨论下个迭代方向（10分钟）
```

### 演示规范

【必须】演示在**真实环境**（测试环境）中进行，不接受 PPT 截图

【必须】只演示已满足完成定义（DoD）的功能；DoD 的定义和示例见 [验收标准规范](acceptance-criteria.md)，此处不重复

【推荐】由研发演示，体现技术实现；产品补充业务背景

## 上线评审规范（可选）

发布前是否召开上线评审、何时召开，由项目自行决定。召开时，可按下表检查；发布步骤、回滚和监控的具体做法见版本的 `engineering/release.md` 和工程清单，本页不规定顺序和形态。

| 检查项 | 说明 |
|--------|------|
| 功能范围 | 此次上线的功能清单（已全部通过测试） |
| 发布顺序 | 有依赖关系时，各部分的发布顺序（如数据库变更、后端、前端） |
| 回滚方案 | 出问题时如何回滚（参考回滚策略规范） |
| 监控告警 | 上线后关注哪些指标，由谁关注 |
| 通知计划 | 是否需要提前通知用户 |
| 灰度策略 | 是否灰度发布，灰度范围（如适用） |

## 评审记录规范

【必须】每次正式评审需有书面记录：

```markdown
## 需求评审记录 - 2026-04-14

**评审功能**：用户头像上传

**参与人**：产品（张三）、研发（李四）、测试（王五）

**结论**：需修改后复评

**待确认事项**：
1. 头像大小限制是 5MB 还是 10MB？负责人：张三，截止：2026-04-15
2. 非正方形图片是否需要裁剪？负责人：张三，截止：2026-04-15

**下次评审时间**：2026-04-16 待确认事项解决后
```

评审记录的落档位置：需求评审的结论和待确认事项写入 `requirements.md` 的「待确认问题」节；设计评审的结论写入 `design-spec.md`；对范围或口径的修改走 SOP-04 并在 `CHANGES.md` 记录。需要保留完整会议记录时，可放在版本目录的 `product/` 下（如 `product/review-notes.md`，项目自行决定，非模板文件）。
