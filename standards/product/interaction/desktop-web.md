# 桌面端 Web 交互规范

> 本规范是 [UI/UX 设计规范](../ui-ux-standards.md) 的细分补充。  
> UI/UX 设计规范定义通用界面原则；本规范定义桌面端 Web 产品中的具体交互行为、组件选择、状态反馈和验收检查。

## 适用范围

适用于桌面优先的 Web 产品，尤其是：

- 后台系统
- 工具型产品
- 数据分析产品
- 搜索和筛选产品
- 内容管理系统
- 工作流产品
- 决策支持产品

不适合作为品牌视觉规范、营销页规范或移动端专项规范使用。

## 核心原则

好的桌面端 Web 交互必须回答四个问题：

1. 我在哪里？
2. 我能做什么？
3. 我操作后发生了什么？
4. 下一步最有用的动作是什么？

如果一个交互方案不能清楚回答这些问题，就不应进入实现。

## 与 UI/UX 设计规范的关系

| 范围 | 遵循规范 |
|------|---------|
| 颜色、排版、间距、基础可访问性、表单基础规则 | [UI/UX 设计规范](../ui-ux-standards.md) |
| 桌面端页面行为、组件选择、状态反馈、CTA 层级、浏览器历史、键盘路径 | 本规范 |
| 交互类验收条件 | 本规范 + [验收标准规范](../acceptance-criteria.md)；落档位置为 [需求文档模板](../../../versions/v1.0.0/product/requirements.md) 的「验收标准」 |
| 原型交付 | 本规范 + [原型设计规范](../prototype-design.md) |

如果两者同时适用，底线是：

- 不降低可访问性
- 不制造误导性交互
- 不破坏用户任务连续性
- 不让错误或失败吞掉用户已经输入的内容

## Must / Should / Avoid

### Must

- 每个有意义的用户动作都必须有明确反馈。
- 看起来可点击的元素必须真的可交互；只展示信息的元素不得使用按钮样式、手型光标、hover 强调或整卡点击暗示。
- 按钮触发动作，链接负责跳转，标签页切换同一语境下的平级视图，展开控件显示可选内容。
- 重要区域应在需要时定义正常、加载、空、无结果、成功、错误、权限和恢复状态。
- 对有意义的状态变化，浏览器返回和前进必须可信。
- 键盘用户必须可以完成主要流程。
- 提交失败或可恢复错误必须保留用户已经输入的内容和上下文。

### Should

- 桌面端空间允许时，主导航应保持可见。
- 一个页面或局部区域默认只保留一个主动作。
- 扫描和比较任务可以高密度；表单和编辑任务保持中等密度；解释和引导任务保持较低密度。
- 渐进展开应用于可选复杂度，而不是隐藏完成任务必需的信息。
- 重要交互应定义可观察的成功或失败信号。

### Avoid

- 避免把主动作藏在 hover、右键或快捷键里。
- 避免没有解释的禁用状态。
- 避免用会很快消失的提示承载关键或可操作信息。
- 避免用弹窗承载很长、探索型或需要上下文对照的任务。
- 避免把标签页、卡片、折叠面板或锚点当作信息架构不清的补丁。

## 常见交互模式选择

| 模式 | 适用 | 不适用 | 验收检查 |
|------|------|--------|---------|
| 左侧边栏导航 | 模块多、结构会增长、用户频繁切换区域 | 页面很浅或阅读型内容为主 | 用户能知道当前位置、同级区域和切换方式 |
| 顶部导航 | 一级目的地少且稳定，或承载全局工具 | 深层或持续增长的工作流导航 | 顶部导航不承担深层定位的全部压力 |
| 面包屑 | 真实层级或下钻路径 | 浏览历史、筛选状态、流程进度 | 每一级都对应真实上级位置 |
| 标签页 | 同一语境下的平级视图切换 | 顺序阅读、并排比较、宽泛目的地导航 | 选中状态清楚，慢内容不突然自动切换 |
| 卡片 | 一个对象或主题需要摘要展示 | 主要任务是密集对比或整卡点击含义不清 | 卡片可点击时，结果符合表面主意图 |
| 表格 | 需要按列比较、检查模式、行级或批量操作 | 卡片、列表或详情页更符合任务 | 全局动作、行级动作、批量动作、排序和选择可区分 |
| 搜索 | 内容集合较大，用户需要直接查找未知项 | 内容很少或自然浏览即可完成 | 搜索范围清楚、结果数量可见、无结果有恢复路径 |
| 筛选 | 用户用已知属性缩小结果集 | 真正任务是搜索、排序或导航 | 已应用筛选可见，可清空，空结果说明原因 |
| 弹窗 | 短、聚焦、必须处理或关闭的中断任务 | 长任务、探索任务、需要上下文对照的任务 | 焦点限制在弹窗内，关闭后焦点回到合理位置 |
| 抽屉 / 侧边面板 | 补充信息或相关任务需要与主上下文并存 | 内容很少、纯确认动作、需要完整页面 | 可完成或放弃侧边任务，且不丢失主页面上下文 |
| 页面锚点 | 长页面有稳定区块且用户需要快速跳转 | 点击后真正需要的是原地获得更多判断或任务支持 | 锚点表现为明确导航，不伪装成卡片反馈 |
| 渐进展开 | 高级或可选细节在需要时出现 | 隐藏完成主任务所必需的信息 | 触发、展开内容和下一步动作形成连贯任务 |

## 状态与反馈规则

任何依赖数据、权限、服务、搜索、筛选或用户输入的区域，应按实际需要定义：

- 默认状态
- hover / focus / active 状态
- 选中或展开状态
- 加载状态
- 成功状态
- 空状态
- 无结果状态
- 表单校验错误
- 权限错误
- 系统错误
- 撤销、重试、取消路径

每个状态都应说明：

- 发生了什么
- 用户还能做什么
- 是否保留用户输入
- 焦点在哪里
- 是否需要屏幕阅读器播报

## CTA 层级规则

- 一个页面或局部区域默认只有一个主 CTA。
- 主 CTA 必须对应当前页面最重要的用户任务。
- 次要动作不能在视觉上抢夺主 CTA。
- 危险动作必须与普通动作明显区分，并说明确认、撤销或恢复方式。
- overflow 菜单中的动作不得是完成主任务所必需的动作。
- 如果页面没有主 CTA，应能解释为什么当前页面以阅读、判断或选择为主。

## 浏览器历史与状态保持

对用户有意义的状态变化，应明确：

- 是否改变 URL
- 是否支持深链接
- 浏览器 Back / Forward 是否恢复状态
- 刷新后是否保留状态
- 滚动位置是否重要
- 选中、展开、筛选、排序、分页状态是否需要保留

筛选、搜索、分页、排序、详情下钻、可分享结果页等通常需要认真考虑浏览器历史和状态保持。

## 键盘与可访问性补充

基础可访问性遵循 [UI/UX 设计规范](../ui-ux-standards.md)。桌面端交互还应补充：

- 主流程可仅用键盘完成。
- 焦点顺序符合任务顺序。
- 焦点状态清楚可见。
- 弹窗、抽屉和原地更新应定义焦点进入、移动和返回。
- hover 才能看到的信息，也应能通过 focus 获得。
- 图标按钮、动态错误、成功和加载状态应有必要的语义说明。
- 不得让快捷键覆盖常见浏览器、系统或辅助技术快捷键。

## 通用验收清单

- [ ] 页面有一个清楚的主要目的。
- [ ] 主 CTA 清楚，或有意不设置主 CTA。
- [ ] 相似元素行为一致。
- [ ] 信息元素不伪装成交互元素。
- [ ] 可交互元素有明确反馈。
- [ ] 每种关键状态都有内容和恢复路径。
- [ ] 浏览器返回和前进行为可预期。
- [ ] 主流程可以仅用键盘完成。
- [ ] 焦点可见且顺序合理。
- [ ] 空状态和无结果状态说明原因和下一步。
- [ ] 错误保留用户输入并说明恢复方式。
- [ ] 重要交互有可观察的成功或失败信号。

## AI Agent 使用规则

当 AI Agent 被要求创建或评审桌面端 Web 交互方案时：

1. 如果存在真实页面、录屏、截图、原型、数据或代码，应先检查真实材料。
2. 如果本轮没有检查真实材料，必须把建议标记为假设。
3. 先说明用户任务、当前状态、交互对象、用户意图和系统反馈，再选择组件模式。
4. 输出交互方案时，应覆盖状态反馈、CTA 层级、浏览器历史、键盘可访问性和验收检查。
5. 需要固定产物时，可使用 [桌面端 Web 交互模板](desktop-web-templates.md)。
