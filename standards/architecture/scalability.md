# 可扩展性设计规范

> **主标准**：[AKF Scale Cube](https://akfpartners.com/growth-blog/scale-cube)（X/Y/Z 三轴扩展模型，与技术栈无关）
> **副标准1**：[DDIA - Designing Data-Intensive Applications](https://dataintensive.net/)（数据层扩展原则）
> **副标准2**：[The Twelve-Factor App - Concurrency](https://12factor.net/concurrency)（进程并发模型）

---

## 核心原则

1. **先设计可扩展性，后优化**：系统初期就应该能横向扩展，而不是到了瓶颈再重构
2. **无状态是扩展的前提**：有状态的服务无法水平扩展，状态必须外化
3. **按需扩展，不过度设计**：根据实际数据决策，而非假设场景

---

## AKF Scale Cube 三轴模型

AKF Scale Cube 将扩展性分为三个独立的维度，可单独或组合使用：

```
          Y 轴（功能/服务拆分）
          ↑
          │
          │
          └──────────────────→ X 轴（水平复制）
         /
        /
       ↙ Z 轴（数据分片）
```

---

### X 轴：水平复制（Horizontal Duplication）

最简单的扩展方式：**运行更多相同的服务实例**，通过负载均衡分发流量。

```
用户请求
    ↓
负载均衡
  ├──→ 服务实例 1
  ├──→ 服务实例 2
  └──→ 服务实例 3
```

**前提**：服务必须是**无状态**的（Twelve-Factor App 第 VI 条）。

**适用场景**：
- 无状态 API 服务、计算型服务
- 读多写少的服务
- 应对突发流量（弹性伸缩）

**扩展方式**：
- 手动：修改副本数配置
- 自动：基于 CPU/QPS 指标的自动扩缩容（如 K8s 的 HPA）

**局限**：所有实例共享同一套数据，数据层仍是瓶颈。

---

### Y 轴：功能/服务拆分（Functional Decomposition）

按**功能职责**拆分服务，不同功能独立部署、独立扩展。

```
单体应用
    → 用户服务（User Service）
    → 订单服务（Order Service）
    → 商品服务（Product Service）
    → 通知服务（Notification Service）
```

**适用场景**：
- 不同功能的负载差异大（如商品查询远多于下单）
- 不同功能需要独立扩展
- 团队按业务域划分

**局限**：服务拆分增加了系统复杂度（分布式事务、服务治理）。

---

### Z 轴：数据分片（Data Partitioning）

按**数据维度**分片，每个实例只处理部分数据。

```
按用户 ID 分片（取模）：
  用户 1-100万    → 分片 1（实例集群 A）
  用户 100-200万  → 分片 2（实例集群 B）
  用户 200-300万  → 分片 3（实例集群 C）
```

**分片策略选型**：

| 策略 | 方式 | 优点 | 缺点 |
|------|------|------|------|
| **哈希分片** | `hash(key) % N` | 均匀分布 | 扩容时需重新 rehash |
| **一致性哈希** | 虚拟节点环 | 扩容影响少（~1/N 数据迁移）| 实现复杂 |
| **范围分片** | 按时间/ID 范围 | 范围查询友好 | 可能热点不均 |
| **业务分片** | 按租户/地区 | 业务隔离 | 跨分片查询困难 |

**适用场景**：
- 单表数据量过大（> 500 万行且查询性能下降，参考值，与 [数据库设计规范](database-design.md) 的分表信号一致）
- 写入 QPS 超过单库上限
- 多租户系统（按租户分片）

**局限**：跨分片查询复杂，事务支持困难。

## 无状态化设计

X 轴扩展的前提。所有可扩展服务必须无状态：

| 有状态 → 无状态 | 改造方式 |
|----------------|---------|
| 本地会话（Session）| 移到 Redis（分布式 Session）|
| 本地缓存 | 移到 Redis / 分布式缓存 |
| 本地文件上传 | 移到对象存储（如 S3 / OSS / COS）|
| 本地锁 | 移到分布式锁（Redis/Zookeeper）|
| 进程内队列 | 移到消息队列 |

```
❌ 有状态：用户请求必须路由到同一实例（会话亲和性）
✅ 无状态：任意实例都能处理任意用户的请求
```

## 读写分离

数据库读写分离是 X 轴扩展在数据层的应用：

```
写操作 → 主库（Primary）
           ↓ 复制（异步/半同步）
读操作 → 从库 1（Replica）
       → 从库 2（Replica）
       → 从库 3（Replica）
```

**注意事项**：
- 复制存在延迟（通常 < 1s，极端情况更长）
- 写后立即读可能读到旧数据 → 写后的读操作走主库（读己所写一致性）
- 从库宕机不影响写操作，提升可用性

---

## 缓存层扩展

多级缓存是提升读扩展能力的关键：

```
用户请求
   ↓
CDN（静态资源/全局缓存）
   ↓
进程内缓存 L1（毫秒级，进程内存）
   ↓
分布式缓存 L2（Redis，毫秒级，跨实例）
   ↓
数据库（持久化）
```

命中率越高，数据库压力越低。目标：**L1+L2 命中率 > 90%**。

---

## 异步解耦

将同步处理改为异步，提升系统吞吐量：

```
❌ 同步：用户下单 → 等待：创建订单+锁库存+扣余额+发通知 → 返回结果
✅ 异步：用户下单 → 立即返回 → 后台队列：创建订单→锁库存→扣余额→发通知
```

**峰值削平（削峰填谷）**：

```
流量高峰 → MQ 缓冲 → 消费者匀速处理
（消息积压，但系统不崩溃）
```

## 扩展性度量指标

| 指标 | 说明 | 目标参考 |
|------|------|---------|
| **线性扩展比** | 实例数 × 2，吞吐量应接近 × 2 | > 0.8（有状态损耗越低越好）|
| **扩容时间** | 从发现瓶颈到扩容生效 | < 5 分钟（自动弹性）|
| **单点故障数** | 系统中无法横向扩展的组件数量 | 趋近于 0 |
| **数据倾斜度** | 分片间数据量/QPS 的最大/最小比 | < 3（避免热点分片）|

## 扩展性设计决策树

```
系统遇到性能瓶颈
  ↓
1. 瓶颈在哪里？（用四个黄金信号定位）
   ├─ CPU / 内存 → X 轴：增加服务实例
   ├─ 数据库读 → 读写分离 + 缓存
   ├─ 数据库写 → Z 轴：分库分表
   └─ 特定功能 → Y 轴：独立服务扩展

2. 是否可以横向扩展？
   ├─ 是（无状态）→ 直接增加实例
   └─ 否（有状态）→ 先无状态化，再扩展

3. 是否需要数据分片？
   ├─ 单表 > 500 万行（参考值）且查询性能下降，或写入 QPS > 单库上限 → Z 轴分片
   └─ 否 → 读写分离 + 索引优化
```
