# 微服务拆分规范

> **主标准**：[Martin Fowler - Microservices](https://martinfowler.com/articles/microservices.html)（微服务架构特征定义）
> **副标准1**：[Sam Newman - BFF Pattern](https://samnewman.io/patterns/architectural/bff/)（Backend for Frontend 模式）
> **副标准2**：[Sam Newman - Building Microservices](https://samnewman.io/books/building_microservices/)（服务拆分原则）
> **副标准3**：[OAuth 2.0 / OIDC](https://oauth.net/2/)（认证服务标准）

---

## 微服务定义（Martin Fowler）

概括自 Martin Fowler 的定义：微服务架构是将一个应用构建为**一组小型、独立可部署的服务**，每个服务：

- 围绕**业务能力**组织，而非技术功能
- 运行在**独立的进程**中
- 通过**轻量级机制**（HTTP/gRPC/消息队列）通信
- 可以用**不同技术栈**实现
- **独立部署**，不依赖其他服务的发布

---

## 微服务架构层次

一个典型的微服务系统由以下层次组成：

```
客户端（Web / App / 第三方）
         ↓
   API 网关（Gateway）       ← 统一入口：路由、认证、限流、日志
         ↓
   BFF 层（可选）            ← 面向特定客户端的聚合适配
         ↓
  ┌──────────────────────────────────┐
  │      原子微服务集群               │
  │  用户服务 | 订单服务 | 商品服务  │  ← 核心业务域服务
  │  支付服务 | 通知服务 | ...       │
  └──────────────────────────────────┘
         ↓
  基础设施服务
  │  认证服务（Auth）                ← 统一身份认证
  │  配置中心                        ← 集中配置管理
  │  服务注册与发现                  ← 服务定位
  └──────────────────────────────────
```

## 服务拆分原则

### 按业务能力拆分（Martin Fowler）

【必须】服务按**业务能力**（Business Capability）拆分，而非按技术层（Controller/Service/DAO 各一个服务）。

```
✅ 正确：用户服务 / 订单服务 / 商品服务 / 支付服务
❌ 错误：数据层服务 / 业务逻辑服务 / 展示层服务
```

### 单一职责

每个服务只负责一个明确定义的业务域，职责边界清晰：

```
✅ 用户服务：用户注册、登录、资料管理
✅ 订单服务：下单、订单状态流转、退款
❌ "用户订单服务"：把两个业务域混在一起
```

### 数据独立性（Sam Newman）

【必须】每个服务**独占自己的数据库**，不允许跨服务直接查询数据库：

```
✅ 服务 A 通过 API 调用服务 B 获取数据
❌ 服务 A 直接 SELECT 服务 B 的数据库表
```

跨服务数据一致性通过**最终一致性**（消息队列）处理，而非分布式事务。

### 服务粒度判断

| 信号 | 说明 |
|------|------|
| 独立部署频率不同 | 应该拆分成独立服务 |
| 团队独立负责 | 一个团队对应一个或多个服务 |
| 技术栈差异大 | 可以拆分，各用最合适的技术 |
| 业务边界模糊 | 先不要拆，在单体中找清楚边界 |
| 服务职责过于单薄（只有很少的逻辑，且总与其他服务一起变更）| 可能过度拆分，考虑合并 |

## API 网关（Gateway）

API 网关是所有外部请求的**统一入口**，承担以下职责：

| 职责 | 说明 |
|------|------|
| **路由** | 将请求路由到对应的后端服务 |
| **认证鉴权** | 验证 Token，拒绝未认证请求，不放到业务服务 |
| **限流** | 对接口和用户进行频率限制 |
| **日志/追踪** | 统一记录请求日志，注入 `requestId` |
| **协议转换** | 外部 HTTP → 内部 gRPC（可选）|
| **SSL 终止** | HTTPS 在网关层解密，内部可以 HTTP |

**网关不应该做的事：**
- 不处理业务逻辑
- 不访问数据库
- 不依赖业务服务的内部实现

```
外部请求 → 网关（认证 → 限流 → 路由）→ 后端服务
                ↓失败
            返回 401/403/429（网关层处理，不透传）
```

## BFF（Backend for Frontend）

### 什么是 BFF（Sam Newman）

BFF 是一种**为特定客户端定制的后端聚合层**：不同的客户端（Web、App、小程序、第三方）对数据的需求不同，与其让一个通用 API 兼容所有客户端，不如为每种客户端建一个专属的 BFF。

```
Web 客户端     ──→ Web BFF      ─┐
iOS App        ──→ Mobile BFF  ─┤──→ 原子微服务集群
Android App    ──→ Mobile BFF  ─┤
第三方         ──→ Open BFF    ─┘
```

### BFF 的职责

| 职责 | 说明 |
|------|------|
| 数据聚合 | 调用多个下游服务，合并成客户端需要的数据结构 |
| 格式适配 | 针对客户端特性做字段裁剪、格式转换 |
| 业务编排 | 将多个原子操作编排成业务流程（如下单 = 创建订单 + 锁库存 + 扣余额）|
| 客户端缓存策略 | 为不同客户端设置不同的缓存 TTL |

### BFF 不应该做的事

- 不处理核心业务规则（放在原子服务）
- 不直接访问数据库（通过原子服务获取数据）
- 不做跨 BFF 的逻辑复用（公共逻辑下沉到原子服务）

### 何时需要 BFF

| 需要 BFF | 不需要 BFF |
|---------|----------|
| 多端数据需求差异大 | 只有一种客户端 |
| 需要聚合多个服务 | API 简单，一对一映射 |
| 前后端团队独立 | 团队规模小 |

## 认证服务（Auth Service）

### 设计原则

认证逻辑**集中在认证服务**，业务服务不负责认证，只负责授权检查。

```
用户登录 → 认证服务（颁发 Token）
请求到达 → 网关（验证 Token）→ 业务服务（从 Token 读取用户信息，做业务授权）
```

### 技术标准（OAuth 2.0 + OIDC）

| 标准 | 用途 |
|------|------|
| **OAuth 2.0** | 授权框架，定义 Token 颁发和使用流程 |
| **OIDC（OpenID Connect）** | 基于 OAuth 2.0 的身份认证标准，增加 `id_token` |
| **JWT（JSON Web Token）** | Token 格式，包含用户信息，无需查库验证 |

### Token 设计规范

```
Access Token：
- 短有效期（15 分钟 ~ 2 小时）
- 包含：用户 ID、角色、权限范围
- 由网关验证，不需要查数据库

Refresh Token：
- 长有效期（7 天 ~ 30 天）
- 存储在服务端（如 Redis 等），可撤销
- 用于换取新 Access Token
```

【必须】Access Token 中不存储敏感信息（手机号、身份证号等）

【必须】业务服务从 Token 中读取用户信息，禁止从请求参数接收用户身份（防止伪造）

### 多端认证场景（示例）

下表是常见客户端形态的示例，项目按实际存在的端取舍。Token 存储位置的取舍详见 [认证授权设计规范](../security/auth-design.md)。

| 端 | 认证方式 | 说明 |
|----|---------|------|
| Web 应用 | 账号密码 + 短信验证码等 | Access Token 推荐存 `HttpOnly` Cookie（配合 CSRF 防护），不推荐存 `localStorage` |
| 移动端 App | 手机号/第三方登录 | JWT，存设备安全存储 |
| 第三方 | OAuth 2.0 Client Credentials | 机器对机器，无用户参与 |
| 内部服务间 | mTLS 或内部 JWT | 服务账号，不走用户认证 |

## 原子微服务（Atomic Microservices）

原子微服务是系统的**核心业务层**，每个服务对应一个明确的业务域：

### 设计标准

【必须】每个原子服务满足以下条件：

1. **独立数据库**：不共享数据库，不直接查其他服务的表
2. **API 契约清晰**：对外暴露 RESTful API 或 gRPC，版本化管理
3. **无状态进程**：不在内存中存储状态，可以随时扩缩容
4. **独立部署**：可以不依赖其他服务单独发布
5. **领域事件发布**：业务状态变更通过事件通知，不直接调用其他服务

### 服务间通信

| 调用方式 | 适用场景 | 注意 |
|---------|---------|------|
| **同步 HTTP/gRPC** | 需要立即获取结果 | 增加耦合，下游不可用时影响上游 |
| **异步消息队列** | 不需要立即响应 | 解耦，需要处理幂等和最终一致性 |

【推荐】**优先使用异步消息**，减少同步调用链路，提升整体可用性。

## 服务治理

### 服务注册与发现

服务启动时向注册中心注册自己的地址，调用方通过注册中心发现目标服务：

```
服务 A 启动 → 注册到注册中心（etcd/Consul/Nacos）
服务 B 调用 A → 从注册中心查询 A 的地址列表 → 负载均衡选一个调用
```

### 服务网格（Service Mesh）可选

对于服务数量多（> 10 个）、跨语言的场景，可引入 Service Mesh（如 Istio）：
- 统一处理服务间的 mTLS、链路追踪、流量管理
- 与业务代码解耦，通过 Sidecar 代理实现

## 反模式（不要这样做）

| 反模式 | 问题 | 解决方案 |
|--------|------|---------|
| 分布式单体 | 服务拆了，但数据库共享 | 每个服务独立数据库 |
| 聊天型服务 | 一次请求触发 10+ 个服务调用 | 合并服务或引入 BFF 聚合 |
| 版本耦合 | 服务 A 升级必须同时升级服务 B | 遵循向后兼容，独立发布 |
| 过早微服务化 | 业务边界未稳定就拆分 | 先做单体，后提取服务 |
