# 系统架构设计规范

> **主标准**：[The Twelve-Factor App](https://12factor.net/)（云原生应用通用原则，与云厂商无关）
> **副标准1**：[Clean Architecture（Robert C. Martin）](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)（应用内部分层原则）
> **副标准2**：[C4 Model](https://c4model.com/)（架构文档化标准）

---

## 核心原则

系统架构设计应满足：

1. **可独立部署**：服务可以独立构建、测试、发布，不依赖其他服务的发布节奏
2. **无状态进程**：应用进程本身不持有状态，状态存储在外部（数据库、缓存、消息队列）
3. **配置与代码分离**：所有环境差异（密钥、地址、端口）通过环境变量注入，代码仓库中不存配置值
4. **可观测性**：日志、指标、链路追踪是一等公民，不是事后添加的功能

## 十二要素原则（Twelve-Factor App）

适用于所有后端服务。

### I. 基准代码（Codebase）

【必须】一个服务对应一个代码仓库，多套部署（开发/测试/生产）共用同一套代码，通过配置区分环境。

```
✅ 一个仓库 → 多套部署
❌ 多个仓库共享同一套代码（使用 submodule 或复制）
❌ 一个仓库包含多个服务（Monorepo 需要额外规范约束）
```

### II. 依赖声明（Dependencies）

【必须】通过包管理工具显式声明所有依赖，不依赖系统全局安装的工具或库。

```
Go:     go.mod / go.sum
Java:   pom.xml / build.gradle
Python: requirements.txt / pyproject.toml
Node:   package.json / package-lock.json
```

### III. 配置（Config）

【必须】所有在不同部署环境间变化的配置，通过**环境变量**注入，不硬编码在代码中，不提交到版本控制。

```bash
# ✅ 从环境变量读取
DB_HOST = os.getenv("DB_HOST")

# ❌ 硬编码
DB_HOST = "db.example.internal:3306"
```

判断一个配置是否应该放在环境变量中：**如果把它开源会有安全风险，就应该在环境变量中。**

### IV. 后端服务（Backing Services）

【必须】数据库、缓存、消息队列、邮件服务等，都作为**可替换的附加资源**，通过 URL/配置连接，不与代码耦合。

```
数据库更换（MySQL → PostgreSQL） → 只改配置
缓存更换（本地 → Redis）       → 只改配置
```

### V. 构建、发布、运行（Build/Release/Run）

【必须】严格分离三个阶段：

```
构建（Build）：代码 → 可执行制品（镜像/二进制）
发布（Release）：制品 + 配置 → 待部署单元（带版本号）
运行（Run）：在目标环境执行发布单元
```

【禁止】在运行阶段修改代码。发布单元不可变，版本号唯一。

### VI. 进程（Processes）

【必须】应用作为**无状态进程**执行，进程间不共享内存，会话等需要持久化的数据存入外部存储（Redis、数据库）。

### VII. 端口绑定（Port Binding）

【必须】服务通过端口绑定对外暴露，自包含 HTTP 服务器，不依赖外部容器（如 Tomcat）注入。

### VIII. 并发（Concurrency）

【推荐】通过增加进程实例数（横向扩展）来提升处理能力，不依赖单进程的垂直扩展。

### IX. 易处理（Disposability）

【必须】进程可以快速启动（秒级）和优雅关闭（处理完当前请求再退出），支持随时被终止和重启。

```
优雅关闭步骤：
1. 停止接受新请求（从负载均衡摘除）
2. 等待当前请求处理完成（设置最大等待时间）
3. 关闭连接池和资源
4. 退出进程
```

### X. 环境一致性（Dev/Prod Parity）

【必须】开发、测试、生产环境尽量保持一致：使用相同的中间件版本、相同的操作系统基础镜像，减少"在我机器上能跑"问题。

### XI. 日志（Logs）

【必须】日志作为**事件流**处理，进程只负责将日志写到 stdout/stderr，由基础设施（容器平台/日志采集器）负责收集、存储、分析。

```
✅ 写到 stdout，由 Filebeat/Fluentd 采集
❌ 直接写到日志文件，应用自己管理文件轮转
```

### XII. 管理任务（Admin Processes）

【必须】数据库迁移、一次性脚本等管理任务，作为**一次性进程**运行，使用与主应用相同的代码仓库和环境，不在生产服务器上直接手动执行。

## 应用分层原则（Clean Architecture）

应用内部代码按依赖方向分层，内层不依赖外层：

```
┌─────────────────────────────────┐
│  Infrastructure（基础设施层）    │  数据库、HTTP 框架、消息队列客户端
│  ┌───────────────────────────┐  │
│  │  Interface（接口层）       │  │  Controller、消费者、事件处理器
│  │  ┌─────────────────────┐  │  │
│  │  │  Application（应用层）│  │  │  Use Case、业务流程编排
│  │  │  ┌───────────────┐  │  │  │
│  │  │  │ Domain（领域层）│  │  │  │  实体、业务规则、领域事件
│  │  │  └───────────────┘  │  │  │
│  │  └─────────────────────┘  │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
         依赖方向：由外向内 →
```

**依赖规则：**
- 内层（Domain/Application）对外层（Interface/Infrastructure）一无所知
- 外层通过接口（Interface）依赖内层，不直接依赖实现
- 数据库、框架、UI 等细节放在最外层，可替换

## 架构文档化（C4 Model）

【推荐】使用 C4 模型的 4 个层次记录架构：

| 层次 | 受众 | 描述内容 |
|------|------|---------|
| **Context（系统上下文）** | 所有人 | 系统与外部用户/系统的关系 |
| **Container（容器）** | 开发/运维 | 系统由哪些可运行/可部署单元组成 |
| **Component（组件）** | 开发 | 每个容器内部的主要组件和交互 |
| **Code（代码）** | 开发（可选）| 具体类/函数级别的设计 |

## 架构决策记录（ADR）

【推荐】重大架构决策使用 ADR（Architecture Decision Record）文档化，记录背景、决策、理由和后果，便于后来者理解"为什么这样选"。

ADR 的格式、编号规则和存放位置使用面板的 ADR 模板：[ADR 模板](../../foundation/tech-arch/decisions/ADR-001-example.md)，模板中的 ADR 索引维护在 `foundation/tech-arch/overview.md`。本页不另带一套格式。
