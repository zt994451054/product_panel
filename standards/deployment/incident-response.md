# 故障响应规范

> **主标准**：[Google SRE - Managing Incidents](https://sre.google/sre-book/managing-incidents/)
> **副标准**：[Google SRE - Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)

本页是通用底线和可选做法；本项目实际做法见 [运维与发布画像](../../engineering/docs/ops-profile.md)。

本页管服务恢复和复盘。缺陷的记录和修复走面板流程：生产缺陷按 [SOP-00.6](../../agents/sop/SOP-00.6-production-bugs.md) 确认环境、分级并归档到 [生产缺陷池](../../foundation/product/production-bugs.md)，处理策略由使用者决定；需要紧急修复时走 SOP-11 热修复。

---

## 故障分级

级别与 SOP-00.6 的生产缺陷分级一致。响应时限由项目定义，写入运维与发布画像。

| 级别 | 定义 | 典型示例 |
|------|------|---------|
| **P0 - 阻断** | 核心服务完全不可用，影响所有用户 | 支付系统宕机、全站 5xx |
| **P1 - 严重** | 核心功能严重降级，影响大量用户 | 下单失败率 > 10%，核心接口 P99 > 10s |
| **P2 - 一般** | 功能部分异常，影响部分用户 | 某类查询超时，非核心功能不可用 |
| **P3 - 轻微** | 轻微异常，用户基本无感知 | 偶发报错、日志告警 |

## 故障响应流程

```
1. 检测（Detection）
   ├─ 自动告警（监控系统触发）
   └─ 用户反馈（客服、用户报告）

2. 响应（Response）
   ├─ 负责人确认告警（有值班安排时由值班人员确认）
   ├─ 初步判断影响范围和级别（P0/P1/P2/P3）
   └─ P0/P1：立即通知相关负责人

3. 缓解（Mitigation）—— 优先于根因分析
   ├─ 能回滚就先回滚（见回滚规范）
   ├─ 无法回滚：降级/限流/重启
   └─ 目标：在项目定义的 RTO 内恢复服务

4. 根因分析（Root Cause Analysis）
   ├─ 服务恢复后开始，不要在故障中浪费时间分析根因
   └─ 需要改代码时按 SOP-00.6 选择处理策略，紧急修复走 SOP-11

5. 事后复盘（Postmortem）
   └─ 默认 48 小时内完成，聚焦改进而非追责
```

**关键原则：先恢复服务，再分析原因。**

## Runbook（操作手册）规范

【推荐】每个核心服务维护 Runbook，告警触发时按手册操作。

**Runbook 模板：**

````markdown
# {服务名} - {告警名称} Runbook

## 告警说明
- 告警条件：XXX
- 影响范围：XXX 用户
- 预期 RTO：X 分钟

## 诊断步骤

### 1. 确认影响范围
```bash
# 查看错误率（示例）
curl https://grafana.example.com/...

# 查看服务实例状态（示例：Kubernetes）
kubectl get pods -n production
```

### 2. 常见原因及处理

**原因1：上游服务不可用**
- 症状：外部调用超时告警
- 处理：降级到缓存结果 + 通知上游团队

**原因2：数据库连接耗尽**
- 症状：连接池等待队列 > 100
- 处理：重启服务 / 检查慢查询

### 3. 升级条件
- {时长} 内未恢复 → 升级级别，联系 {升级对象}（由项目定义）
````

## 故障中的沟通（可选做法）

按团队规模取舍。单人或小团队至少记下事件时间线，复盘要用。

**P0/P1 故障期间建议：**

1. 建立专属沟通渠道（渠道和命名由项目定义）
2. 指定一名**指挥官（Incident Commander）**负责协调，其他人负责具体操作
3. 定期同步进展（频率由项目定义，如每 15 分钟；没有新进展也更新"正在排查中"）
4. 故障解除后发布恢复通知

**指挥官职责（Google SRE 模式）：**
- 不参与技术操作，专注于协调和决策
- 向管理层和受影响团队汇报进展
- 决定何时升级（叫更多人）、何时降级

## 事后复盘（Postmortem）

### 无责文化（Blameless Postmortem）

【必须】复盘关注**系统和流程的改进**，不针对个人追责。原则：

> "假设参与者在当时的信息和条件下做出了最合理的决策。"（意译自 Norm Kerth《Project Retrospectives》的回顾最高指导原则）

### 复盘模板

```markdown
# Postmortem：{故障简述} - {日期}

## 故障摘要
- 影响时长：XX 分钟
- 影响范围：XX 用户受影响
- 严重级别：P{0-3}
- 根本原因：一句话总结

## 事件时间线
| 时间 | 事件 |
|------|------|
| 10:00 | 监控告警触发 |
| 10:05 | 值班人员确认 |
| 10:15 | 识别根因 |
| 10:25 | 回滚完成，服务恢复 |

## 根因分析
（描述根本原因，而非表面现象）

## 触发因素
（是什么直接导致了故障，通常不是根本原因）

## 缓解措施
（本次故障中采取了哪些措施缓解影响）

## 预防措施（带负责人和截止日期）
| 措施 | 负责人 | 截止日期 | 状态 |
|------|--------|---------|------|
| 添加自动回滚 | {负责人} | YYYY-MM-DD | 进行中 |
| 补充 Runbook | {负责人} | YYYY-MM-DD | 待开始 |
```

### 复盘要求

【必须】P0/P1 故障必须做 Postmortem，默认 **48 小时内**完成（项目可在运维与发布画像中调整）

【必须】Postmortem 中的 Action Item 必须指定负责人和截止日期

【推荐】Postmortem 结果分享给整个技术团队，避免同类错误重复发生

## 值班（On-Call）（可选做法）

【推荐】按服务等级定义值班覆盖范围，写明谁响应 P0/P1、覆盖哪些时段。小团队或开源项目可以不设值班，但要写清楚故障发生时找谁。

**值班设计原则（Google SRE）：**
- 值班不应该太频繁：同一人每月值班不超过 25%（避免 burnout）
- 告警必须可操作：值班人员不应该经常因为无意义告警被打扰
- 有 Runbook：值班人员不需要知道所有细节，按手册操作即可
