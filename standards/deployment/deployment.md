# 部署规范

> **主标准**：[Google SRE - Release Engineering](https://sre.google/sre-book/release-engineering/)
> **副标准**：[Martin Fowler - Patterns for Managing Source Code Branches](https://martinfowler.com/articles/branching-patterns.html)

本页是通用底线和可选做法；本项目实际做法见 [运维与发布画像](../../engineering/docs/ops-profile.md)。

---

## 部署底线

不管用什么基础设施，每次生产部署都要做到：

1. **先在非生产环境验证**：制品在至少一个非生产环境验证通过后才进生产，见 [CI/CD 流水线规范](ci-cd.md)
2. **向后兼容**：新旧版本可能并存时，API 和数据格式必须兼容；Schema 变更用扩展-收缩方式，先扩展后使用，见 [回滚策略规范](rollback.md)
3. **部署前有回滚方案**：写在 `versions/{ver}/engineering/release.md` 的「回滚方案」节
4. **生产做业务链路验证**：部署后实际走一遍核心业务链路。健康检查通过只说明进程活着，不代表功能可用。面板的生产验收见 [AGENTS.md](../../AGENTS.md) SOP-12
5. **有发布记录**：步骤、结果和遗留事项记录在 `versions/{ver}/engineering/release.md`

## 部署策略（可选做法）

根据系统规模、风险承受度和基础设施能力选择合适的策略：

| 策略 | 零停机 | 回滚速度 | 流量控制 | 资源成本 | 适用场景 |
|------|--------|---------|---------|---------|---------|
| 直接替换 | ❌ | 中（重新部署上一个制品）| 无 | 低 | 单机部署、内部工具、可接受短暂停机的服务 |
| 滚动发布 | ✅ | 中（需重新部署）| 无 | 低 | 多实例服务的常见选择 |
| 蓝绿部署 | ✅ | 快（秒级切流）| 全量切换 | 高（双倍资源）| 核心高风险服务 |
| 金丝雀发布 | ✅ | 快 | 精细（%流量）| 中 | 大流量、需灰度验证 |
| 特性开关 | ✅ | 极快（改配置）| 任意维度 | 低 | 长期灰度、A/B 测试 |

## 滚动发布（Rolling Update）

逐批替换旧实例为新实例，始终保持服务可用。

```
初始状态：[v1][v1][v1][v1]

第一批：  [v2][v1][v1][v1]  ← 替换 25%
第二批：  [v2][v2][v1][v1]  ← 替换 50%
第三批：  [v2][v2][v2][v1]  ← 替换 75%
完成：    [v2][v2][v2][v2]  ← 替换 100%
```

**关键参数（以 Kubernetes 为例，可选）：**
- `maxUnavailable`：滚动期间最多有多少实例不可用（常见取值 25%）
- `maxSurge`：滚动期间最多可以创建多少额外实例（常见取值 25%）

```yaml
# Kubernetes 滚动更新配置
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 25%
    maxSurge: 25%
```

**注意事项**：
- 新旧版本会**同时运行**，API 必须向后兼容
- 数据库 Schema 变更必须在代码部署前完成（先扩展，后迁移）
- 进行中的请求必须优雅完成（Graceful Shutdown），参考高可用规范

## 蓝绿部署（Blue-Green Deployment）

维护两套完全相同的生产环境（蓝/绿），通过负载均衡切换流量。

```
部署前：负载均衡 → 蓝（v1）  绿（空闲）

部署中：
  1. 将 v2 部署到绿色环境
  2. 在绿色环境运行完整测试
  3. 将负载均衡流量切换到绿色

部署后：负载均衡 → 绿（v2）  蓝（v1，保留用于回滚）

回滚：将负载均衡切回蓝色（秒级）
```

**优点**：回滚极快（秒级），部署期间不影响用户

**缺点**：需要双倍资源；Session 管理需要处理（用户可能在切换时从 v1 切到 v2）

**适用场景**：核心交易系统、对可用性要求极高的服务

## 金丝雀发布（Canary Release）

将少量流量导入新版本，验证后逐步扩大比例。

```
初始：   [v2 5%] ←── 5% 流量
         [v1 95%] ←── 95% 流量

验证通过后逐步扩大：
         [v2 20%] → [v2 50%] → [v2 100%]
```

**流量分配维度**：
- 按比例（5% → 20% → 50% → 100%）
- 按用户属性（内部用户、Beta 用户、特定地区）
- 按请求特征（特定设备类型、特定 API 版本）

**晋级标准**（满足才扩大比例，指标和阈值由项目定义，下表为示例）：

| 指标 | 阈值示例 |
|------|------|
| 错误率 | ≤ 老版本的 1.5 倍 |
| P99 延迟 | ≤ 老版本的 1.2 倍 |
| 业务成功率 | ≥ 老版本的 99% |

## 特性开关（Feature Flags）

将功能的发布与代码部署解耦，通过配置控制功能可见性。

```python
# ✅ 代码中使用特性开关
if feature_flags.is_enabled("new_checkout_flow", user=current_user):
    return new_checkout_handler(request)
else:
    return legacy_checkout_handler(request)
```

**用途分类：**

| 类型 | 生命周期 | 用途 |
|------|---------|------|
| 发布开关（Release Toggle）| 短期（功能稳定后清理）| 新功能安全上线，可随时关闭 |
| 实验开关（Experiment Toggle）| 中期（A/B 测试期间）| 对比不同实现的效果 |
| 运维开关（Ops Toggle）| 长期 | 降级开关，高峰期关闭非核心功能 |
| 权限开关（Permission Toggle）| 长期 | 按用户/租户/角色控制功能访问 |

【推荐】发布开关在功能稳定后及时清理，并设清理期限（由项目定），不要永久遗留发布开关

## 部署前检查清单

每次生产部署前必须确认：

```
□ 本版本全部测试用例通过（未通过项只能是使用者逐条豁免并已登记）
□ 已在非生产环境验证
□ 数据库变更脚本已准备并在非生产环境验证（如有）
□ 回滚方案已确认（见回滚规范）
□ 发布后要走的核心业务链路已列出
□ 监控告警已就位
```

测试放行规则以 [AGENTS.md](../../AGENTS.md) SOP-03 的测试底线为准。

可选项（由项目决定是否采用）：

```
□ 部署期间有人值班
□ 已通知相关团队（如影响范围较大）
□ 部署时间在低峰期窗口内（或已确认可在高峰期操作）
```

## 零停机部署（按可用性要求决定）

【推荐】是否要求零停机（Zero Downtime），由服务的可用性目标决定。单实例服务、批处理、静态站等不一定需要。需要时做到：

1. **优雅关闭**：服务收到终止信号（如 SIGTERM）后停止接受新请求，等待当前请求处理完毕再退出
2. **就绪后才接流量**：新实例通过就绪检查（如 Kubernetes readiness probe）后才接受流量
3. **向后兼容**：新旧版本并存期间 API 和数据格式必须兼容
4. **数据库先行**：Schema 变更先于代码部署（先扩展后使用）
