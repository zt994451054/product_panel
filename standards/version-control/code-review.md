# Code Review 规范

> **主标准**：[Google Engineering Practices - Code Review](https://google.github.io/eng-practices/review/)
> **副标准**：[Conventional Comments](https://conventionalcomments.org/)（评论格式规范）

---

## 核心原则（Google Engineering Practices）

> "Code review 的主要目的是确保代码库的整体质量随时间持续提升。"

1. **代码库质量 > 个人偏好**：审查者的意见应基于客观标准，而非个人风格偏好
2. **完美是好的敌人**：不要因为代码不够"完美"就无限期阻塞合并，只要整体质量有提升就应该批准
3. **尊重作者**：评论针对代码，不针对人
4. **速度很重要**：Review 延迟直接影响团队交付效率，非紧急情况应在**1 个工作日内**响应

---

## 审查者应该关注什么

按优先级排序：

| 维度 | 说明 |
|------|------|
| **设计** | 代码与系统整体架构是否协调，交互是否合理 |
| **功能** | 代码是否实现了预期功能，边界情况是否处理 |
| **复杂度** | 是否过度复杂，能否更简单地实现 |
| **测试** | 是否有合适的测试，测试是否能真正验证功能 |
| **命名** | 变量/函数/类名是否清晰表达意图 |
| **注释** | 复杂逻辑是否有必要的注释（why，不是 what）|
| **文档** | 相关文档是否同步更新 |
| **风格** | 是否符合代码风格规范 |

**不应该关注的**：个人风格偏好（只要符合规范），除非有客观的理由。

## 如何给出评论（Conventional Comments）

使用 [Conventional Comments](https://conventionalcomments.org/) 格式，让评论意图明确：

```
<label> [decorations]: <subject>
[discussion]
```

**常用标签：**

| 标签 | 含义 | 是否阻塞合并 |
|------|------|------------|
| `issue` | 指出具体问题，通常需要修改 | 加 `(blocking)` 装饰时阻塞 |
| `suggestion` | 建议修改，但不强制 | ❌ |
| `question` | 不理解，需要作者解释 | 视情况 |
| `nitpick` | 小问题，可选修复 | ❌ |
| `praise` | 肯定好的做法 | ❌ |
| `thought` | 分享想法，不要求行动 | ❌ |
| `todo` / `note` / `chore` | 待办事项 / 提示说明 / 需完成的杂项 | 视情况 |

`blocking` 在 Conventional Comments 中是装饰（decoration），写在标签后的括号里（如 `issue (blocking):`），表示必须修改才能合并；`non-blocking` 表示不阻塞。

```markdown
issue (blocking): 这里的 SQL 查询没有使用参数化，存在 SQL 注入风险。
建议改为：db.Query("SELECT * FROM users WHERE id = ?", id)

suggestion: 这个函数超过 80 行了，考虑拆分为几个小函数？

nitpick: 这里的变量名 `d` 不够清晰，可以改成 `duration` 吗？

praise: 这个错误处理写得很好，考虑了所有边界情况！
```

**重要**：评论要对事不对人：

```
✅ "这里有个边界情况没有处理：当 list 为空时会 panic"
❌ "你怎么没想到 list 为空的情况"

✅ "suggestion: 这个逻辑可以用 map 替代 for 循环，时间复杂度从 O(n²) 降到 O(n)"
❌ "这个写法太低效了"
```

## 审查者行为规范

### 响应时间

【必须】非紧急 PR 在**1 个工作日**内给出首次回应（不一定完成，但要告知何时完成）

【必须】作者修改后，审查者应在**1 个工作日**内重新审查

### 审查深度

【必须】理解代码的实现逻辑，而非只看大致方向

【必须】自己能看懂才批准，不确定的要提问

【推荐】跑一下代码，特别是关键功能或复杂逻辑

### 当有分歧时

【必须】审查者和作者有分歧时，优先**当面/视频沟通**，不要无限期在评论区争论

如果仍有分歧，找第三方（技术负责人或更有经验的同学）裁决

## 作者行为规范

### 提交 PR 前

【必须】自己先 Review 一遍（能发现大量低级错误）

【必须】PR 描述清楚：做了什么、为什么这样做、如何测试

【推荐】PR 大小控制在 **200-400 行**（含测试），超过难以有效 Review

```markdown
## 变更内容
（简述做了什么）

## 变更原因
（为什么要这样改）

## 测试方式
（怎么验证这个改动是对的；用例、通过标准遵守 SOP-03 测试底线）

## 关键设计决策（可选）
（做了哪些非显而易见的选择？为什么这样选而不是其他方案？）

## 考虑过的其他方案（可选）
（有哪些备选方案被排除，以及排除原因）

## 已知局限（可选）
（这个改动有什么未处理的边界情况、临时妥协或后续待跟进事项？）

## 注意事项（可选）
（审查者需要特别关注的地方）
```

### 响应评论

【必须】对每条评论都要回复（即使只是 "Done" 或 "已修改"）

【必须】不同意审查者意见时，要解释原因，而不是静默忽略

【推荐】修改后在对应评论线程回复修改了什么

## PR 大小规范

| PR 大小 | 状态 | 处理方式 |
|---------|------|---------|
| < 100 行 | ✅ 理想 | 正常 Review |
| 100-400 行 | ✅ 可接受 | 正常 Review |
| 400-800 行 | ⚠️ 较大 | 说明无法拆分的原因 |
| > 800 行 | ❌ 过大 | 必须拆分，除非是生成代码或文件重命名 |

**为什么控制 PR 大小：**
- 大 PR Review 质量低（审查者疲劳，漏看细节）
- 大 PR 合并冲突多，阻塞其他人
- 小 PR 反馈更快，迭代更快

---

## 紧急修复（Hotfix）的 Review

生产故障紧急修复时，允许简化 Review 流程，但**事后必须补充完整 Review**；简化的只是 Review，测试底线（SOP-03、SOP-11）不放宽：

```
正常：PR → Review → 合并
紧急：口头确认（或单人 Review）→ 合并 → 事后补 Review + Postmortem
```
