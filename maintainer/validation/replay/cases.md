# L3 历史回放用例

来源：下游项目在真实使用中踩过的问题，已去除项目与业务细节，只保留与面板机制相关的情景。
评审方法：评审者只读面板文档（AGENTS.md、SETUP.md、standards/、versions/ 模板等，不读 maintainer/），对每条情景判断面板能否预防或及时发现：

- **拦截**：有明确规则，且规则位于该情景必经的流程节点上（SOP 步骤、门控、模板必填项）
- **部分**：有相关规则，但表述含糊、不在必经节点上、或只覆盖一部分
- **无**：面板中没有能拦住该情景的规则

每条给出判定与依据（文件:行号）。

## 需求与范围

| 编号 | 情景 | 期望面板的拦截点 |
|---|---|---|
| H01 | 一个版本在多次需求变更中范围被悄悄扩大，负责人直到发布前才发现 | 变更登记时标注范围影响；范围扩大须负责人确认 |
| H02 | 需求依赖的外部事实（第三方能力、实现前提）未经验证就签收，开发阶段实测被推翻 | 需求中列出待验证假设，含未验证关键假设的需求不得确认 |
| H03 | 已拍板的决策在后续重做设计时被违背，靠使用者记忆拦下 | 决策有集中记录，重新设计前核对 |
| H04 | AI 把使用者未答复的事项写成「已同意」，或把简短回答扩大解读 | 决策记录引用原话；不得把沉默当同意 |
| H05 | 未立项需求的调研记录被写进不相关版本的变更记录 | 未立项调研有固定落点 |

## 设计与技术方案

| 编号 | 情景 | 期望面板的拦截点 |
|---|---|---|
| H06 | 测试验收通过，但 UI 与交互没有按原型高保真还原 | 开发要求还原；测试用例含还原检查；退出条件含还原 |
| H07 | 原型持续迭代，测试时无法确定对照的是哪一版原型 | 设计文档固定原型基准 |
| H08 | 把兼容性、性能等验收项当成开发准入门禁，长时间只写文档不写代码；核心可行性反而拖到验收才验证 | 进入开发须有核心实现路径的验证；验收项不作开发门禁；停滞预警给出收缩方案 |
| H09 | 修复问题时另起一套机制，没发现系统里已有同类设计 | 开发前检索既有机制 |
| H10 | 发布约束、生产结构变更与回滚可行性到写上线手册时才发现互相矛盾 | 技术方案阶段写明发布可行性 |

## 测试设计与执行

| 编号 | 情景 | 期望面板的拦截点 |
|---|---|---|
| H11 | 技术方案完成后直接进入开发，没有先写测试计划和用例 | 阶段顺序含测试设计；进入开发的门控检查测试计划与用例 |
| H12 | 测试用例只覆盖需求文档，漏掉设计稿与改动影响的已有功能 | 用例覆盖全部新特性点与改动点，有覆盖对照 |
| H13 | 用例预期写成「显示正常」，执行者理解不一 | 用例四要素必填，禁止模糊预期 |
| H14 | 测试计划没检查能否执行，执行时才暴露环境、设备、账号、需人在场等阻塞 | 测试计划含执行就绪检查，进入测试门控核对 |
| H15 | 全部界面测试都在非生产默认配置下跑，生产默认配置下的阻断缺陷到发布前才暴露 | P0 主流程按生产默认配置执行 |
| H16 | 测试环境与生产不等价（数据、配置、启动方式），差异未登记 | 登记测试环境与生产的差异 |
| H17 | 测试中反复出现的人工干预（如系统弹框）被当成环境噪声，上线后成为用户可见缺陷 | 人工干预须判定是否产品缺陷 |
| H18 | 部分用例失败或原型有偏差，仍以「条件通过」推进发布 | 全部用例通过才放行；豁免只能由使用者逐条明示 |
| H19 | 子 agent 自行判定用例通过；AI 自审后把阶段标为完成 | 完成判定须有依据，AI 自审不等于签收 |
| H20 | 用例统计在多处手工同步，长期不一致 | 统计只维护一处或自动生成 |
| H21 | 缺陷修复改变了原有设计约定，用例和技术方案没回写 | 缺陷关闭前检查是否需回写 |
| H22 | 回归范围靠拍脑袋，要么全量扩测，要么漏测 | 回归范围有影响分析方法，裁剪须确认 |
| H23 | 测试数据（种子、账号）没有生命周期管理，残留或无法恢复 | 测试数据有登记与清理要求 |

## 发布、生产与运维

| 编号 | 情景 | 期望面板的拦截点 |
|---|---|---|
| H24 | 发布前只在测试环境验证结构变更，而测试环境早已有新结构，发布时出错 | 发布前提含生产结构比对与发布、回滚演练 |
| H25 | 发布后只看健康检查和登录页，核心业务链路故障由用户报告才发现 | 发布后须做业务链路的生产验证 |
| H26 | 生产从非发布分支上线，面板状态与线上不一致 | 上线完成核对版本标识；门禁外上线有例外流程 |
| H27 | 版本收尾项（合并打标、基线合并、清理临时资源、归档）靠使用者追问才补 | 版本收尾清单 |
| H28 | 热修复只修了主线，没有回灌到在研版本 | 热修复收尾时逐个在途版本确认 |
| H29 | 部署方式、配置来源等基础设施变更不经评估就上生产，引发事故 | 基础设施变更有影响分析与验证流程 |
| H30 | 流水线随版本累积版本专用步骤，与最初设计漂移 | 流水线只做通用动作，版本操作在发布文档 |
| H31 | 构建、部署、工具接入方式只存在某台机器或某个 AI 的记忆里 | 这些信息在面板中有固定落点 |
| H32 | AI 操作外部系统时被工具默认值加了额外配置，事后才发现 | 外部写操作须逐项授权、写后回读核对 |

## 面板治理与协作

| 编号 | 情景 | 期望面板的拦截点 |
|---|---|---|
| H33 | 新建的顶层目录被白名单 .gitignore 静默忽略，大量文件长期未入库 | 新建目录同步白名单；有检查手段 |
| H34 | 在研或搁置的版本只登记在功能分支，主线看不到；版本号撞号 | 主线登记全部在途版本；立项先占号 |
| H35 | 多个会话共用一个工作区，未提交改动长期堆积，正式文档引用了未提交内容 | 工作区与分支纪律 |
| H36 | 下游合并上游模板时，自有 SOP 因编号冲突被静默丢失 | SOP 编号与引用一致性检查；升级指南 |
| H37 | 复盘结论没有转成规则；长期约束只说给了某个 AI，只存在其私有记忆里 | 复盘以规则候选结尾；规则只认面板 |
| H38 | AI 回复使用者看不懂：内部代号、一次抛十几个决策、长会话后切换语言 | 面向使用者的表达规范 |
| H39 | 使用者睡前交代无人值守运行，缺少决策盘点和预授权，运行中卡在需人在场的步骤 | 自主运行前做决策盘点与预授权，标注需人在场的步骤 |
| H40 | 派发的子 agent 不知道红线与交付物，越界或交付不全 | 子 agent 派发须带红线与交付物定义 |
| H41 | 交接说明写「已完成」，实际只写了文档没有改代码 | 交接结论标证据等级，接手方先核对 |
| H42 | 凭据值被写进面板或打印到会话输出 | 凭据只记名称与位置；输出脱敏 |
| H43 | 文档、证据、截图大量入库，仓库膨胀 | 大附件外置，仓库只留清单 |
