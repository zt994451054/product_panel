## 4. 面板缺陷

### 高

无。

### 中

**M1. 冒烟运行结果没有规定的记录位置**
- 位置：testing/smoke/README.md 规则 1（第 18 行）只规定写法（「通过 N / 失败 N / 跳过 N」，写明跳过哪条），「启用后的附加要求」（第 50-53 行）只覆盖测试计划、提测说明、release.md、SOP-13 四个场景。
- 现象：本场景的部署验证发生在技术方案阶段，不属于提测或发布，执行 agent 只好在模块文件里自建「运行记录」节（smoke/README.md:68 起）。模块文件既放规则又放持续增长的日志，不同 agent 会各自选位置，结果不好追溯。
- 建议：在 smoke 模块里明确「提测、发布之外的冒烟结果（含测试环境部署验证）写在哪」。可以在模块文件末尾预置固定格式的「运行记录」表（只留最近 N 次），或写明记入 environments.md / ops-changes.md 对应条目；同时说明在流水线自动跑、使用者没问时是否需要记录。

### 低

**L1. 「未启用不读模块文件」与「建议启用」有张力**
- 位置：SETUP.md:56「未启用时 AI 不读模块文件」；AGENTS.md:27「需求或对话里出现某模块的需要…向使用者建议启用」；三个模块文件第 3 行「未启用时 AI 不读本文件」。
- 现象：执行 agent 建议启用时，回复里已经用到只出现在模块文件里的措辞。第 2 轮第一次回复「文案母版（所有译文的唯一来源）」（T:54，对应 i18n/README.md:22），第 4 轮第一次回复「回答『这次部署能不能用』」（T:153，对应 smoke/README.md:4）。可以推断，它在使用者同意前读过模块文件。要向使用者说清模块是什么、启用后要填什么，读文件几乎绕不开，规则写成「不读」过于绝对。
- 建议：改成「未启用时不执行模块规则、不在状态摘要中提示；需要向使用者建议启用时，可以读模块文件开头的说明和『启用时要做』，用来解释启用后要做什么」。

**L2. SOP-13 没说未决定的运维变更要不要登记，状态枚举里也没有「待决定」**
- 位置：agents/sop/SOP-13-ops-change.md 步骤 1；engineering/docs/ops-changes.md 状态枚举「分析中 / 测试环境已验证 / 生产已执行 / 已完成 / 已回滚」。
- 现象：SOP-04:7 明确写了「想法还没决定要改，不登记」，SOP-13 没有对应条款。执行 agent 登记了 AI 提议的 OPS-001，状态自造为「未获决策」。
- 建议：SOP-13 补一句（未决定时是否登记、怎么标），状态枚举加「待决定」。

**L3. 「无法核实身份时写『当前使用者』」只写在 SOP-03**
- 位置：agents/sop/SOP-03-testing.md:14。SETUP.md:64「记录列写确认人」、communication.md §4 决策记录、decisions.md 模板都没有这条。
- 现象：执行 agent 自行把它推广到 SETUP 记录、decisions.md、backlog，做法合理，但依据不在通用规则里。
- 建议：把这条移到 communication.md §4 或 collaboration.md，作为通用写法。

**L4. i18n「已有文案没进母版的，列为待办」没写列在哪**
- 位置：standards/i18n/README.md:16。
- 现象：执行 agent 把待办写在勾选框后的括注里，后续没有跟踪位置。
- 建议：写明列在版本 CHANGES 影响项、requirements 待确认，还是 i18n 文件里的专门小节。

**L5. 路线图候选什么时候进需求池没写**
- 位置：foundation/planning/README.md 规则 1（第 18 行）；roadmap.md「进入版本」列。
- 现象：使用者只说「帮我记一下」，执行 agent 在记路线图的同时登记了 REQ-001。面板没说路线图候选是否同步进需求池，换一个 agent 可能就不登记，两种做法都不违规。
- 建议：写明「路线图候选不自动进需求池，使用者说要做时再登记」，或者反过来写明要同步登记，二选一。

**L6. SOP-04 步骤 7 对「草稿模块写进已确认的 requirements.md」口径不清**
- 位置：agents/sop/SOP-04-change.md:23「未确认前在 CHANGES.md 标『待确认』，不写进 requirements.md」。
- 现象：执行 agent 在已确认的 requirements.md 里新增了状态为「草稿」的多语言模块，包括 AI 起草的 4 条验收标准、Q-001、Q-002、A-002（requirements.md:134 起），并标了「AI 起草，待确认」。按字面可以读成违反步骤 7，也可以读成步骤 7 只管「已确认需求」。
- 建议：明确扩大范围、已获同意的变更，新模块能否以「草稿」状态先写进 requirements.md。

## 5. 其他观察

- **场景设计问题，不算面板缺陷**：
  - 预设用例「取消预约」在沙箱 v1.0.0 需求里没有对应功能，requirements.md 只在第 55 行的提示文案里出现「取消」二字。
  - 沙箱停在技术方案阶段，却让使用者说「部署测试环境后冒烟跑完了」。
  - 执行 agent 把这两处矛盾都指出来了（T:171、T:201），说明对齐意识好。如果场景本意不考这一点，可以把冒烟用例换成需求内的功能，或说明测试环境部署的是旧版或骨架。
- **未经同意的小改动**：第 2 轮填了版本 README 范围表的两行原有功能，没有单独告知使用者（见 S10-02）。第 1 轮问过「版本说明背景和目标要不要补」，使用者没答复；范围表虽然不在那个问题里，但第 1 轮也把它列为「对不上的地方」，填写前应一并说明。
- **注意力分配**：第 1 轮主动核对了技术方案阶段的门控条件，并发现 A-001 状态与实测结论不一致、DESIGN.md 与配置状态不一致，这些后续轮次都持续跟踪了。
- **提交处理**：第 6 轮没有自动提交，说明了等复核后再提交，并请使用者给指令，这一点合理。
