# 面板规则变更记录

记录本项目对面板规则的修改：AGENTS.md、`agents/` 下的文件，以及 `SETUP.md` 的配置项定义。产品规范（`standards/`）的修改不记在这里，在 `standards/README.md` 改状态即可；版本内的需求、方案变更记在 `versions/{ver}/CHANGES.md`。

## 规则

- **只有写进面板的才是规则**。对某个 AI 说过、存在 AI 私有记忆里的约定，要长期生效就记一条并改对应文件
- **编号在合入主线时分配**：在分支上写 `RULE-待定`，合入主线时按顺序编号，避免多条分支撞号
- **复盘的结论**以「规则候选」结尾，每条标「采纳」或「否决」及理由；采纳的在这里记一条并改规则，否决的留在复盘文档里

## 格式

```markdown
## RULE-{三位编号} | {YYYY-MM-DD} | {一句话标题}

**来源**：使用者的原话或决定（谁、什么时候），或复盘文档路径
**改动**：改了哪些文件、哪条规则，改前改后各一句
**影响**：对进行中的版本、其他分支有什么影响；没有写「无」
```

## RULE-待定 | 2026-11-27 | 用例改为用命令登记和记录执行结果

**来源**：架构师 2026-11-27「整个优化的过程，你按照你的想法来继续推进……确实你自己判断不了的时候，你再来找我来确认」。此前他已同意「先做决定和变更两类记录、用例放下一批」；这一批的具体做法由 AI 按同一思路决定
**改动**：
- 新增命令 `case add` / `case result` / `case regress` / `case waive` / `case list`：用例先登记拿编号（TC 编号改为命令分配），`--items` 关联需求条目，草稿条目不能登记用例；每执行一次记一次结果，必须写实际看到了什么；失败和阻塞一次一条；使用者转述的结果一次一条并带他的原话；豁免只能由成员本人逐条做
- 命令自动把已通过的用例退回「需回归」：关联的需求条目变更、关联的缺陷记为已修复、版本进入「测试」阶段（改前靠 AI 记得去改表格）。关联用例没有重新通过时，缺陷不能记为待验收
- 门控自动核对：签收「测试设计」要每条需求条目都有用例，签收「开发中」要 P0 用例都有自测通过的记录（演练里有模型靠使用者一句话就放行了这条，之后补上），签收「测试」要用例全部通过或已豁免
- `defect open --case` 只认登记过的用例编号
- `status` 显示各状态的用例数；驾驶舱版本详情页增加用例列表
- `test-cases.md` 去掉「用例总览」表、执行状态、验收状态和详情里的执行记录，只留覆盖矩阵、评审和用例内容；逐条用例的「验收状态（人工）」取消，人的把关落在缺陷验收关闭、逐条豁免和「测试」阶段签收上。`test-report.md`「豁免登记」只补未通过原因和后续去向，其余以命令记录为准
- SOP-03 改为命令流程；SOP-04（需回归）、SOP-05（自测记录）、SOP-07（门控）、SOP-11、AGENTS.md §2、§6、§7，`agents/state.md` §3、§5、§9，`testing/docs/test-strategy.md` 相应修改
- 顺带修正：豁免范围在事件里和事件自身的所属范围重名，查看时显示成了版本号（缺陷豁免同样受影响），已改字段名
- 演练后补充：SOP-07 去掉「按口述放行的条件先用 `decision add` 登记」这一步。门控记录本身已经带说话人和原话，再登记一遍会被「一句话只记一处」拒绝，演练里三个模型有两个因此作废决定重记
**影响**：进行中的版本要把已有用例用 `case add` 补登记、已有结果用 `case result` 补记（补记用 `--at` 和 `--backfill`），否则「测试设计」「测试」两个阶段签收不了；生产验收用例（`acceptance.md`）这一批没有改，仍在文档里维护

## RULE-待定 | 2026-11-27 | 决定和变更改为用命令记录

**来源**：架构师 2026-11-27 两次答复「按建议」。第一次指上一条逐条列出的三条：先做决定和变更两类记录、用例放下一批；两份文档去掉表格只留叙述；只能靠模型自觉的几项不再加规则文字，在说明文档里写成已知局限。第二次指上一条逐条列出的三条：「你决定」「都行」这类话命令拒绝记成决定；范围扩大的变更必须引用已登记的决定；驾驶舱版本详情页加决定和变更两个列表
**改动**：
- 新增命令 `decision add` / `decision list`：原话和「指的是哪条建议」分成两栏；原话里带「（指：……）」、原话是「你决定」「都行」「按规范来」一类的，命令拒绝；「按建议」「可以」这类短话必须写明指的是哪条；推翻旧决定用 `--replaces`
- 新增命令 `change open` / `change affect` / `change handle` / `change close` / `change list`：登记时分配编号并记下时间；范围扩大必须引用一条有效的决定；全部受影响的文档处理完、并有成员的原话才能完结；`item change --ref` 只认登记过的变更编号
- `status` 列出每条没完结的变更还差哪几份文档、有效的决定有几条；驾驶舱版本详情页显示两个列表
- `decisions.md` 去掉表格，只留规则和补充说明；`CHANGES.md` 去掉变更汇总表、处理状态和勾选框，只留叙述
- SOP-04 重写为先登记后修改的命令流程；AGENTS.md §2、§3、§5.1、§6、§7，`agents/state.md` §3、§5、§9，`agents/communication.md` §4，SOP-00、01、02、03、06、07、11、12、13，`agents/collaboration.md`，版本内各模板，以及两份规范文件相应修改
- README 写明旗舰级模型仍会偶尔漏掉的四件事
- 演练后补充（架构师 2026-11-27「你按照你的想法来继续推进……确实你自己判断不了的时候，你再来找我来确认」之后由 AI 自行决定）：`change handle` 增加 `--pending`，文档改了但还留着没确认的内容时注明，注明后一直显示在状态里、变更不能完结；需求条目的优先级随条目一起确认，草稿条目在列表里标「未确认」，`item confirm` 可带 `--priority`。SOP-04 第 5 步、SOP-01 相应修改
**影响**：进行中的版本要把已有的决定和变更用命令补登记一遍（补记用 `--at` 和 `--backfill`）；已有的旧编号继续可用，但 `item change --ref` 要先有对应的 `change open` 记录

## RULE-待定 | 2026-11-26 | 成员记下熟悉的领域，AI 按此调整说明（软引导）

**来源**：架构师 2026-11-26 的决定：「记录到成员记录记录当中，换一个电脑也都知道」「领域的话可以先就定这六个」「如果它的领域已经分好了的话，其实默认就是熟悉」「关于边界的拓展，这个就是让 AI 来提示吧」；提示依据「可以放宽吧」；项目管理改名「总之就是这个产品的 owner」
**改动**：
- 成员记录新增「熟悉的领域」（`member add` / `member update` 的 `--familiar`）：产品、前端、后端、测试、运维、总负责人六个（「总负责人」是对产品整体负责的人，名称由面板取，区别于各版本的负责人），不分熟悉程度，选了的就是熟悉；没记的按都熟悉对待。和「负责域」分开，不影响谁能签收、谁能决定
- `status` 第一行显示当前操作者熟悉的领域；他在清单以外的领域做过决定时给一条提示（签收阶段、确认需求、修复或验收缺陷、批准生产部署）；总负责人没有对应记录，不自动提示
- `agents/communication.md` §8（新增）、AGENTS.md §5.1 第 7 条、`agents/state.md` §4：没选的领域多解释、给默认建议、讲清签的是什么；不拦任何操作；边界扩大时问一次，由本人回答后更新，AI 不自行增减
- 新加一个领域时告诉他一次之后这块会说得简短、需要细讲随时说（架构师 2026-11-26 对该建议答复「第一个问题可以的」）
- SOP-08、SOP-09：登记成员时顺带问一句平时做哪几块
**影响**：已登记的成员没有这项记录，按都熟悉对待，和原来一样；需要时用 `member update --familiar` 补记

## RULE-待定 | 2026-11-25 | 确认要逐条、依据要核实；撞号和已发布版本的处理

**来源**：架构师 2026-11-25 的决定「其他按照你的建议来」（指上一条逐条列出的五条从严口径）；多人多分支并行与完整发布流程的实测
**改动**：
- `agents/communication.md` §3、§4，AGENTS.md §5.1、§7：笼统的话（「其余都通过」）不算逐条确认；「按建议」不延伸到上一条没列出的事；早先针对别的事说的话不挪用；一条消息里所有要使用者回答的都计入 4 个问题的上限
- SOP-07：门控条件的依据要核实过。只有口述、核实不了的记未通过；使用者明确决定按口述放行的，记决定后再记通过，并在签收摘要里单独列出
- `agents/state.md`：原话必须针对这件事；两人离线记了同一步不算矛盾；撞号后在后建一方的工作区里命令拒绝继续写，作废创建记录后它名下的记录一并失效；已发布的版本不能挂起、放弃、改期、回退，也不做在途确认；热修复版本号必须是补丁号，且要先有已发布版本或生产部署记录
- 需求条目和缺陷的状态改为用命令记录（2026-11-25，架构师「按照建议来」，指需求条目按功能级、复用事件机制、编号用成员标识加本人流水号、示例一并改）：`requirements.md` 去掉「需求状态」列，`defects.md` 去掉缺陷列表和状态列，只留叙述；SOP-01、03、04、05、07、12 相应改为 `item`、`defect` 命令；「需求分析」「测试」「发布」的门控由命令自动核对需求确认情况和缺陷关闭情况
- 全部登记类编号改为「前缀-成员标识-本人流水号」（`agents/state.md` §9）：需求条目、缺陷由命令分配，其余手工按同一规则取；模板和示例里的编号全部改成新格式
**影响**：进行中的版本要把已有的需求清单和缺陷用 `item add`、`defect open` 补登记一遍（补记用 `--at` 和 `--backfill`）；已有的旧编号可以继续用，新登记的按新规则

**来源**：四个模型、四个场景的演练评审（2026-11-25）；架构师「按建议修」（指上一条逐条列出的三条建议）
