# 状态数据与命令

> 项目和版本的状态怎么存、怎么读、怎么改。推进阶段、签收、改负责人、确认配置项、改设置、记部署之前读本页。红线摘要在 AGENTS.md §7。

## 1. 状态存在哪

状态不写在任何文档里。每发生一件事（进入阶段、签收、改期、部署……）就多一个事件文件，写入后不再修改；当前状态是把所有事件按时间重放算出来的。

| 位置 | 内容 |
|------|------|
| `state/events/` | 项目级事件：初始化、成员、签收设置、配置项、可选模块、部署 |
| `versions/{ver}/state/events/` | 该版本的事件：新建、阶段、门控核对、签收、回退、改期、挂起、阻塞、进展 |
| `state/defs/config-items.json` | 配置项的定义（不含状态） |

**不指定权威分支**。读状态时，命令把当前工作区、所有本地分支、所有已拉取的远端分支上的事件合在一起。各版本可以在各自的分支上推进，不需要先合并到某条分支。

## 2. 读状态

```bash
git fetch --all
node tools/panel.mjs status
```

先拉取，别人在其他分支上记的状态才看得到；拉不了就在回复开头说明「没能拉取，状态可能不全」。每次新对话先运行（AGENTS.md §0、§3）。只看某个版本加 `--version v1.1.0`。不要通读事件文件，也不要自己推算阶段和天数。

**给人看的驾驶舱**：

```bash
node tools/panel.mjs render
```

在仓库根目录生成 `cockpit.html`，用浏览器直接打开：各版本的轨道、等谁处理、时间线、数据、可复制的提示词。它只读、不联网、不入库，是生成当时的快照。使用者问「现在什么情况」「帮我打开看板」时生成一份并告诉他文件位置；状态变化后重新生成。AI 自己读状态仍然用 `status`，不读这个页面。

## 3. 改状态

只通过命令改，全部命令见 `node tools/panel.mjs help`。常用：

| 要做的事 | 命令 |
|---------|------|
| 新建版本 | `version new` |
| 进入阶段 | `stage enter` |
| 记录门控核对 | `stage check` |
| 做完了，请人签收 | `stage request` |
| 记录签收 | `stage complete` |
| 阶段回退 | `stage rollback` |
| 写进展说明 | `note` |
| 记阻塞、解除阻塞 | `block`、`unblock` |
| 改计划发布日 | `version replan` |
| 挂起、恢复、放弃 | `version hold`、`version resume`、`version abandon` |
| 记部署、回滚 | `deploy` |
| 发布前确认在途版本 | `downstream-check` |
| 确认配置项 | `config set` |
| 改签收设置 | `settings set` |
| 写错了 | `event void`（作废后重新记一条正确的） |

规则：

1. **每条写命令都指明版本**（`--version`）和操作人（`--by`）。命令不替人猜版本。`--by` 的填法：AI 按流程自己记录的（进入阶段、门控核对、请求签收、记录签收、进展说明、阻塞）写 `ai`；必须由人决定的（初始化、成员、改签收设置、确认配置项、启用或停用模块、挂起、恢复、放弃、声明起点）写做决定的那位成员的标识，他的原话填 `--quote`。做决定的就是当前操作者时写 `me`
2. **原话照录**。`--quote` 只填使用者在对话里实际说的话，不改写、不合并、不补全。使用者没说就不执行这条命令
3. **命令拒绝时不绕过**。它会说明缺什么（如「签收前要先做门控核对」），把原因告诉使用者，补齐后再执行。不改用手写文件，不换一个更宽松的参数
4. **写错了不改文件**。用 `event void` 作废那一条，再记一条正确的
5. **补记历史**：`--at` 填当时的时间；早于该版本已有记录时加 `--backfill "原因"`
6. **写完就提交并推送**。只在本机的事件别人看不到；状态变更和文档改动可以放在同一个提交里。推送面板仓库同样要有使用者的授权（[collaboration.md](./collaboration.md) §2，可以一次授权本次对话内的推送）；没有授权、推不了、或仓库没有配置远端时，只提交不推送，并在回复里照实说明原因（如「这个仓库没有远端，状态只在本机」），不编一个理由
7. **签收的顺序固定**：`stage check` 通过 → `stage request` → 使用者同意 → `stage complete`。命令只认进入本阶段之后最近的一次门控核对
8. **不跳阶段**：`version onboard`（声明起点）只用于存量产品接入；热修复流程只用于修已发布（或按 SOP-00.6 视同已发布）版本的生产缺陷，版本号是补丁号并写明修的缺陷编号。命令会拒绝其他用法
9. **删除分支前**先运行 `node tools/panel.mjs check --branch <分支>`，列出的事件要先合入别的分支，否则会丢

## 4. 当前操作者是谁

需要人做决定的命令要知道「是哪位成员说的」。这来自个人档案 `profile.md`：放在仓库根目录、不入库，第一行是 `member: 成员标识`，说明这台电脑上操作面板的是谁。

- `status` 的第一行会显示当前操作者。显示「未识别」时，在第一次需要人做决定之前问一次「你是哪位成员」，然后运行 `whoami --set <成员标识>` 记下来，之后不再问
- 对方没回答自己是谁：需要人决定的命令都不执行，按「未获决策」处理（AGENTS.md §7），不猜、不替他挑一个成员，也不写「待本人复核」后先记上
- 对话里做决定的明显是另一位成员（如「阿哲说可以」）：`--by` 写那位成员，不写 `me`
- 签收人（`--signer`）同理：当前操作者是该版本的负责人之一时才能记他的签收

## 5. 谁能决定什么

| 事情 | 谁决定 |
|------|-------|
| 阶段签收 | 按该阶段的签收设置（见下）。签收人必须是该版本登记的负责人之一 |
| 「测试」和「发布」两个阶段的签收 | 固定由人签，设置改不了。「发布」只能由产品负责人签 |
| 改签收设置、挂起、恢复、放弃、确认配置项、批准生产部署 | 只能是在册成员本人的决定，AI 不能自己做 |
| 互相矛盾的记录怎么处理 | 使用者。AI 列出处理办法，不自行作废 |
| 批准生产部署 | 在册成员。`deploy` 记录批准人和他批准时说的原话；事后补记的例外上线不知道谁批准的，就不填批准人，不拿别的话顶替。没有本版本的生产部署记录，「发布」签不了 |

签收设置有三种：`human` 人工签收（默认）、`review_human` 评审后人工签收、`auto` 评审团自动放行。后两种需要评审记录，评审记录还没有落地：设置可以先改，但记录签收时命令目前只接受人工签收。

## 6. 状态有问题时

`status` 或 `check` 报出下面的情况时，写在回复开头，由使用者决定：

| 报什么 | 是什么意思 | 怎么办 |
|-------|-----------|-------|
| 有一条记录没有生效 | 两处记录互相矛盾，如同一阶段签收了两次 | 向使用者说明矛盾在哪，列出办法（通常是作废其中一条），使用者决定后执行 |
| 版本号已经被占用 / 属于另一个撞了号的版本 | 两个人各自建了同一个版本号。先建的生效；后建一方在这个版本号下记的所有内容都不生效，也不会落到对方的版本上 | 后建的一方换一个版本号：新建版本目录、把文档移过去、用新版本号重新记录阶段和签收（补记用 `--at` 和 `--backfill`） |
| 事件文件损坏、内容不一致、被删除 | 有人手改或删了事件文件 | 不自行修复。告诉使用者是哪个文件，建议从 git 历史恢复 |
| 没能从 git 读出来 | 本机 git 不可用或仓库异常 | 状态可能不完整，先解决 git 问题再继续 |

## 7. 不能执行命令时

没装 Node、运行环境禁止执行脚本时：

- 可以直接读当前分支上的事件文件了解大致状态，可以写需求、方案等叙述文档
- **不得**推进阶段、记录签收、改设置、确认配置项，也不得手写事件文件代替
- 在回复开头明确告诉使用者：「当前无法运行状态命令，只能读，状态没有更新」，并说明需要本机装有 Node 和 git（工具在 Node 24 上验证过）

## 8. 提交前

```bash
node tools/panel.mjs check
```

有问题会逐条列出。通过后再提交。
