# SOP-07 阶段推进

**触发**：某阶段工作完成，需要标记推进到下一阶段

**阶段顺序**：规划中 → 需求分析 → 产品设计 → 技术方案 → 测试设计 → 开发中 → 测试 → 发布 → 已发布

> 「测试设计」在「开发中」之前：开发开始前必须先有测试计划和测试用例（SOP-03 A），开发自测与提测都以这些用例为依据。

**阶段签收**：阶段标为 ✅ 必须有签收依据，填入版本 README 阶段表的「签收」列：
- 签收 = 使用者（`versions/CURRENT.md` 登记的负责人）明确同意该阶段完成。记录签收人、日期和原话摘要，如「@小林 2026-04-18：技术方案没问题，可以往下走」
- AI 自审、子 agent 评审、检查清单全部打勾，都**不算签收**，只能作为提交使用者签收时的依据
- 使用者回答「你决定」「都行」或未答复，视为未签收，阶段保持 🔄
- 使用者说「继续推进」「开始开发」这类话时，如果还没看过本阶段摘要，不算签收：AI 先给摘要和门控核对结果，请使用者明确确认
- 门控条件须在推进当时逐条核对并写明依据，**不得事后用执行结果反推补勾**

**推进前检查（阶段门控）**：推进前须逐条核查，任一未满足则**拒绝推进**并告知用户缺少什么：

> 每个门控都隐含「上一阶段已签收」，下表不再逐行重复。
> 每个门控都隐含「配置状态表中要求在目标阶段（或更早阶段）之前完成的 L1 项，状态为已确认或不适用」。草稿待审、暂不填、未填都不放行。查 `SETUP.md`，按「产品类型」取对应一列。

| 推进目标 | 必须满足的前置条件 |
|---------|-----------------|
| → 需求分析 | 配置状态表中要求在「需求分析」之前完成的 L1 项已完成（存量产品：产品架构与功能清单）|
| → 产品设计 | `requirements.md` 中所有 P0 功能状态为「已确认」；无未解决的 ⛔ 阻塞型待确认问题；「实现前提与待验证假设」已填写（没有写「无」），未验证的已在确认需求时列给使用者 |
| → 技术方案 | `design-spec.md` 主体内容已填写（非全空占位符）；「原型增量」节已固定原型基准（核对提交存在，映射表的路由在该提交的原型中已实现），页面映射表每个页面已标还原优先级 |
| → 测试设计 | `tech-solution.md` + `api-design.md` + `db-design.md` 均已完成；`tech-solution.md`「核心实现路径验证」节每条路径都有结论和证据；`requirements.md` 中的关键假设：技术 / 外部类都已验证（不成立的已按 SOP-04 改需求或方案），业务 / 用户行为类已由使用者确认接受；版本 `README.md`「发布关键项」表每行已填写（不涉及的填「无」） |
| → 开发中 | `test-plan.md` 测试范围、回归测试范围、测试数据、退出条件已填写，排除测试项和回归裁剪都有使用者逐条同意的决策编号；`test-plan.md`「执行就绪」表已填写；`test-cases.md` 覆盖矩阵无空行（写「未覆盖」「待定」「未定义」的行不算已覆盖，使用者逐条同意不测的写「不测：D-xxx」），每条用例四要素完整、预期可判定；用例独立评审结论为「通过」且无未解决意见；无未解决的阻塞型待确认问题（使用者逐条同意按暂定值推进的算解决，记原话；未答复或笼统确认不算） |
| → 测试 | 功能代码已部署到 staging（用户确认）；CI 流水线通过；相关 P0 用例已自测通过；`test-plan.md` 进入条件已逐条核对并写明依据（含测试环境配置已与生产默认配置核对、执行就绪表每行就绪或使用者已决定处理方式、被测构建已核对） |
| → 发布 | `test-report.md` 结论为「通过」：全部用例通过、全部缺陷关闭，未通过项只能是使用者逐条豁免并已登记；原型还原检查用例全部通过（或逐条豁免）；P0 主流程用例确实按生产默认配置执行；通过结果对应最终被测构建；人工干预全部已判定；本版改动引入的代码检查和自动化测试问题为 0、存量不增加；测试数据已清理或写明保留原因 |
| → 已发布 | `acceptance.md`「版本交付确认」已由产品负责人签收 |

> 门控只看文档是否齐全还不够：签收前，AI 须把本阶段关键内容（如技术方案的核心路径验证结论、用例覆盖矩阵）摘要给使用者，由使用者判断质量。

> ❌ **反例**：用户说「需求写完了，可以开始技术方案了」→ AI 须先检查 requirements.md 是否所有 P0 功能都已确认，有草稿状态则拒绝推进。
> ❌ **反例**：用户说「技术方案你自己审一遍，没问题就标完成」→ AI 可以自审并汇报结果，但不能标 ✅；须请使用者签收。

**步骤（三处文件必须全部同步）：**
1. `versions/{版本}/README.md` 阶段进度表（**时间戳必填**）：
   - 完成阶段：状态改 ✅，**完成时间填今日日期**（YYYY-MM-DD），「签收」列填签收人、日期、原话摘要
   - 新阶段：状态改 🔄，**开始时间填今日日期**（YYYY-MM-DD）
2. `versions/CURRENT.md`：主线开发版本的当前阶段改为新阶段名称，进入时间改为今日日期
3. `versions/README.md` 进度矩阵：对应版本行该阶段格改为 ✅

**完成标志**：三处文件均已同步更新，完成阶段有签收记录

**推进到「已发布」时的额外合并动作**（除三处状态同步外，必做）：

| 源（版本内增量） | 目标（基线） | 合并要点 |
|---------------|------------|---------|
| `versions/{ver}/engineering/api-design.md` 已上线接口 | `engineering/docs/api-docs/openapi.yaml` | 追加新接口；修改已有接口；废弃接口标 `deprecated: true` |
| `versions/{ver}/engineering/db-design.md` 增量 DDL | `engineering/docs/db-schema/full-schema.md` | 按业务模块更新表定义，ERD 同步，变更历史表追加一行 |
| `versions/{ver}/product/requirements.md` 已交付功能 | `foundation/product-arch/overview.md` 模块详情表 | 新功能追加一行（引入版本填本版本号）；功能变更更新对应行 |

**合并完成判定**：三项合并均已完成，基线文档已反映本版本交付结果。
基线不同文档之间存在冲突 → 停止并告知用户，不自行裁量。

> 合并依据见 [全量基线与版本增量](../baselines.md)。未完成合并不得将版本阶段标记为「已发布」。

**示例：技术方案完成，推进到测试设计阶段**
> 用户说：「v1.0.0 技术方案我看过了，没问题，往下走吧」
>
> AI 正确行为：
> ① 核对「→ 测试设计」门控：三份技术文档已完成；核心实现路径验证 2 条均已实测通过；发布关键项已填；使用者已看过这些摘要并明确同意
> ② 更新 versions/v1.0.0/README.md 阶段进度表：
>    | 技术方案 | ✅ 完成   | 2026-04-15 | 2026-04-18 | 含接口与数据库设计 | @李四 2026-04-18：「没问题，往下走」 |
>    | 测试设计 | 🔄 进行中 | 2026-04-18 | -          |                  |  |
> ③ 更新 versions/CURRENT.md：阶段改为「测试设计」，进入时间改为今日
> ④ 更新 versions/README.md 进度矩阵：v1.0.0 行「技术方案」格改为 ✅，「测试设计」格改为 🔄
> ⑤ 接着执行 SOP-03 A 编写测试计划与用例
>
> ❌ 错误行为：直接推进到「开发中」，测试计划和用例留到开发期间或开发后再写

**反例：**
> ❌ 只更新了 CURRENT.md，忘记同步版本 README 和进度矩阵
> ❌ 进展说明留空，没有记录当前阶段的实际进展状态
> ❌ 签收列留空或填「AI 自审通过」

**示例：阶段回退（测试发现严重问题，需要回到开发阶段）**
> 用户说：「测试发现 P0 缺陷 BUG-003，需要回到开发阶段修复」
>
> AI 正确行为（三处文件同步）：
> ① 更新 versions/{ver}/README.md：
>    | 测试     | ↩️ 已回退 | 2026-04-22 | 回退原因：发现 P0 缺陷 BUG-003，需重新进入开发 |
>    | 开发中   | 🔄 进行中 | 2026-04-25 | 修复 BUG-003 |
> ② 更新 versions/CURRENT.md：当前阶段改为「开发中」
> ③ 更新 versions/README.md 进度矩阵：对应版本「测试」格改回 🔄，「发布」格保持 ⏳
>
> ❌ 错误行为：仅在 defects.md 记录缺陷，不更新版本阶段状态
