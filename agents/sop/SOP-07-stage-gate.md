# SOP-07 阶段推进

**触发**：某阶段工作完成，需要标记推进到下一阶段

**阶段顺序**：规划中 → 需求分析 → 产品设计 → 技术方案 → 测试设计 → 开发中 → 测试 → 发布 → 已发布

> 「测试设计」在「开发中」之前：开发开始前必须先有测试计划和测试用例（SOP-03 A），开发自测与提测都以这些用例为依据。
> 热修复版本只走后五个阶段：技术方案 → 测试设计 → 开发中 → 测试 → 发布（SOP-11）。
> 「规划中」「已发布」不是阶段：版本建好还没进入任何阶段是规划中，「发布」阶段签收后是已发布。

**阶段状态只通过命令记录**（[state.md](../state.md)），不写在任何文档里。一个阶段从进入到完成是四步：

| 步骤 | 命令 | 说明 |
|------|------|------|
| 进入阶段 | `stage enter` | 命令会检查顺序和该阶段要求的配置项 |
| 门控核对 | `stage check` | 按下表逐条核对，每条写依据。有一条不满足就是「未通过」 |
| 请人签收 | `stage request` | 把本阶段摘要和核对结果给签收人看 |
| 记录签收 | `stage complete` | 最近一次门控核对通过、之后请求过签收，命令才接受 |

**阶段签收**：一个阶段算完成，必须按该阶段的签收设置取得签收（设置见 `status` 输出或 [state.md](../state.md) §5；默认全部是人工签收）。
- 人工签收 = 该版本登记的负责人之一明确同意该阶段完成。`--signer` 填签收人，`--quote` 填他的原话，如「技术方案没问题，可以往下走」
- 「测试」「发布」两个阶段固定由人签，任何设置都改不了；「发布」只能由产品负责人签
- 签收设置为人工时，AI 自审、子 agent 评审、检查清单全部打勾，都**不算签收**，只能作为提交使用者签收时的依据
- 使用者回答「你决定」「都行」或未答复，视为未签收，不执行 `stage complete`
- 使用者说「继续推进」「开始开发」这类话时，如果还没看过本阶段摘要，不算签收：AI 先给摘要和门控核对结果，请使用者明确确认
- 门控条件须在签收前逐条核对并写明依据，**不得事后用执行结果反推补做**
- **依据要是核实过的**。AI 能自己核实的条件（文件内容、提交、流水线结果、用例状态）必须自己核实，不拿使用者的一句话代替。只有使用者口头说了、AI 核实不了的：
  - 条件本身写明由使用者确认的（下表标「用户确认」的），记通过，依据写「使用者确认：{原话}」
  - 其他条件记**未通过**，依据写「使用者口述『{原话}』，未核实」，并告诉使用者怎样才能核实（给出证据在哪）。使用者针对**这一条**明确说了「按我说的算」时，把这个决定用 `decision add` 登记，再用「按口述」的方式记通过：`--check "条件|ok|未核实，使用者决定按口述放行：{决策编号}|told|成员标识|他针对这一条的原话"`，并在请求签收的摘要里单独列出这些条目。命令要求每条各有各的原话：一句话不能替多条条件作证，签收时说的话也不能拆开当成各条的依据；没有逐条说过的就记未通过
- 核对方式照实写：`script` 是命令或脚本验证的，`manual` 是 AI 自己读了文件、看了记录核实的，`told` 是只听人说、没有核实的。没亲眼看到证据的不写 `manual`
- **核实不了时不停在那里**：把核实不了的条件逐条列给使用者（每条写清为什么核实不了、证据应该在哪），请他逐条选：补证据，或回答「这条按我说的算」。每轮最多 4 条，多的分几轮。他逐条答了就按上面的方式记，再请求签收
- **该记的签收要记**：门控通过、使用者看过摘要后针对本阶段明确说了签收的话，就用 `stage complete` 记下来，不因为「想更稳妥」而不记。门控没通过时他的签收话先不记，告诉他还差哪几条、怎么补
- 使用者说「其余都通过」「都没问题」这类笼统的话，不算对门控条件的逐条确认：把涉及的条件逐条列出再请他确认（[communication.md](../communication.md) §4）

**命令自己核对的条件**：`stage check` 会自动加上两条，不用 AI 数表格，也不能用 `--check` 改写结论。签收「需求分析」时：需求条目已登记，P0 条目全部已确认；签收「测试」和「发布」时：登记的缺陷全部已关闭或已豁免。签收「发布」时还有：线上版本标识已核对（看的是 `deploy` 记录里有没有核对结果，不接受口述）。不满足时先处理（确认需求、关闭或由使用者豁免缺陷），不是换个说法重新核对

**签收前检查（阶段门控）**：签收某个阶段前须逐条核查，任一未满足则**不请求签收**并告知用户缺少什么：

> 进入每个阶段都要求上一阶段已签收，并且配置清单里要求在该阶段（或更早阶段）之前完成的项已确认或不适用；草稿待审、暂不填、未填都不放行。这两条由 `stage enter` 命令检查，下表不再重复。

| 要签收的阶段 | 必须满足的条件 |
|------------|--------------|
| 需求分析 | `requirements.md` 中所有 P0 功能状态为「已确认」；无未解决的 ⛔ 阻塞型待确认问题；「实现前提与待验证假设」已填写（没有写「无」），未验证的已在确认需求时列给使用者 |
| 产品设计 | `design-spec.md` 主体内容已填写（非全空占位符）；「原型增量」节已固定原型基准（核对提交存在，映射表的路由在该提交的原型中已实现），页面映射表每个页面已标还原优先级 |
| 技术方案 | `tech-solution.md` + `api-design.md` + `db-design.md` 均已完成；`tech-solution.md`「核心实现路径验证」节每条路径都有结论和证据；`requirements.md` 中的关键假设：技术 / 外部类都已验证（不成立的已按 SOP-04 改需求或方案），业务 / 用户行为类已由使用者确认接受；版本 `README.md`「发布关键项」表每行已填写（不涉及的填「无」）；`tech-solution.md`「发布可行性」已填写：生产结构比对（只读）和每项变更的回滚可行性，不可逆的已有使用者同意 |
| 测试设计 | `test-plan.md` 测试范围、回归测试范围、测试数据、退出条件已填写，排除测试项和回归裁剪都有使用者逐条同意的决策编号；`test-plan.md`「执行就绪」表已填写；`test-cases.md` 覆盖矩阵无空行（写「未覆盖」「待定」「未定义」的行不算已覆盖，使用者逐条同意不测的写「不测：D-{成员标识}-xxx」），每条用例四要素完整、预期可判定；用例独立评审结论为「通过」且无未解决意见；无未解决的阻塞型待确认问题（使用者逐条同意按暂定值推进的算解决，记原话；未答复或笼统确认不算） |
| 开发中 | 功能代码已部署到 staging（用户确认）；CI 流水线通过；相关 P0 用例已自测通过；`test-plan.md` 进入条件已逐条核对并写明依据（含测试环境配置已与生产默认配置核对、执行就绪表每行就绪或使用者已决定处理方式、被测构建已核对） |
| 测试 | `test-report.md` 结论为「通过」：全部用例通过、全部缺陷关闭，未通过项只能是使用者逐条豁免并已登记；原型还原检查用例全部通过（或逐条豁免）；P0 主流程用例确实按生产默认配置执行；通过结果对应最终被测构建；人工干预全部已判定；本版改动引入的代码检查和自动化测试问题为 0、存量不增加；测试数据已清理或写明保留原因 |
| 发布 | `acceptance.md`「版本交付确认」已由产品负责人签收；release.md「生产业务验证」全部 ✅；「例外上线」没有未补齐的条目；下方「收尾清单」全部完成；其他未发布的版本（含挂起的）都已逐个确认是否合入本版本的改动（`downstream-check`，命令会检查） |

> 门控只看文档是否齐全还不够：签收前，AI 须把本阶段关键内容（如技术方案的核心路径验证结论、用例覆盖矩阵）摘要给使用者，由使用者判断质量。

> ❌ **反例**：用户说「需求写完了，可以开始技术方案了」→ AI 须先检查 requirements.md 是否所有 P0 功能都已确认，有草稿状态则拒绝推进。
> ❌ **反例**：用户说「技术方案你自己审一遍，没问题就标完成」→ 签收设置是人工时，AI 可以自审并汇报结果，但不能记录签收；须请使用者签收。使用者想以后都交给评审，是改签收设置（`settings set`），不是这一次口头放行。

**步骤：**
1. 按上表核对本阶段门控，运行 `stage check` 记录每一条和依据
2. 未通过 → 告诉使用者缺什么，停在这里
3. 通过 → 把本阶段关键内容摘要和核对结果给使用者，运行 `stage request`
4. 使用者明确同意后，运行 `stage complete`，`--quote` 填原话
5. 运行 `stage enter` 进入下一阶段（「发布」签收后没有下一阶段）
6. 提交并推送

**完成标志**：`status` 显示该阶段已签收、下一阶段进行中

**进展、阻塞、改期**：阶段进行中有值得让别人知道的进展，用 `note` 记一句；被卡住用 `block` 记下卡在哪、归谁处理，解决后 `unblock`；计划发布日要改用 `version replan`。这些都会出现在 `status` 里，不另写文档。

**发布阶段内的状态**：部署到生产一完成就运行 `deploy` 记一条，不等生产业务验证通过。批准人的原话必须是他看过发布前提之后、针对这次部署说的，开场时说的「开始发布吧」不算，没有就先问。线上实际的版本标识核对过的，用 `--checked` 写明怎么核对的、读到了什么；还没核对就先不写，`status` 会一直提示「线上版本标识还没核对」，拿到后用 `deploy --action verify --checked …` 补上，不凭「说是部署了」自己填。使用者只说了「回滚吧」「发吧」是决定，不是已经做完：等他说做完了再记。没有这条记录，命令不接受「发布」的签收。部署完成、生产验收进行中时，版本仍在「发布」阶段，`status` 会显示「已部署到生产，发布完成还没签收」。回滚同样用 `deploy --action rollback` 记录，写明回到哪个版本；首次上线回滚没有上一个版本时不写，`status` 会显示线上没有版本。生产业务验证或生产验收中发现缺陷需要修复时，阶段回退到「开发中」（见下方阶段回退示例的「从发布回退」）。

**签收「发布」前的收尾清单**（逐项完成，作为「发布」门控核对的一条写明依据；做不了的项写原因，由使用者决定）：

| 收尾项 | 做什么 |
|-------|-------|
| 合并与标记 | 发布分支合入主干，打版本 tag；tag 指向的提交与线上版本标识一致 |
| 基线合并 | 见下表「额外合并动作」 |
| 生产验收清理 | acceptance.md「分工」约定的验收数据、临时账号已清理 |
| 临时资源 | 发布用的功能开关、临时配置、演练环境已清理或登记保留原因 |
| 分支与 worktree | 为本版本建的分支、worktree 已清理（[collaboration.md](../collaboration.md) §5） |
| 物料归档 | 本版本用到的 `materials/` 资料在 `materials/README.md`「归档」列填本版本号 |
| 线上版本 | `status` 的「线上在跑」是本版本（部署记录齐全，没有未记录的回滚）；`engineering/docs/ops-profile.md`「线上版本」同步 |
| 在途版本 | 其他每个未发布的版本（含挂起的），评估是否需要合入本版本的改动，逐个运行 `downstream-check` 记录结论、依据和确认人的原话（热修复见 SOP-11 第 7 步）。结论写「暂缓」或「部分合入」的，要写明由谁、什么时候补，并在目标版本按 SOP-04 登记一条变更；目标版本的 `status` 会一直显示「还欠一次合入」 |

**签收「发布」前的基线合并**（必做）：

| 源（版本内增量） | 目标（基线） | 合并要点 |
|---------------|------------|---------|
| `versions/{ver}/engineering/api-design.md` 已上线接口 | `engineering/docs/api-docs/openapi.yaml` | 追加新接口；修改已有接口；废弃接口标 `deprecated: true` |
| `versions/{ver}/engineering/db-design.md` 增量 DDL | `engineering/docs/db-schema/full-schema.md` | 按业务模块更新表定义，ERD 同步，变更历史表追加一行 |
| `versions/{ver}/product/requirements.md` 已交付功能 | `foundation/product-arch/overview.md` 模块详情表 | 新功能追加一行（引入版本填本版本号）；功能变更更新对应行 |

**合并完成判定**：三项合并均已完成，基线文档已反映本版本交付结果。
基线不同文档之间存在冲突 → 停止并告知用户，不自行裁量。

> 合并依据见 [全量基线与版本增量](../baselines.md)。未完成合并不得签收「发布」。

**示例：技术方案完成，推进到测试设计阶段**
> 用户说：「v1.0.0 技术方案我看过了，没问题，往下走吧」
>
> AI 正确行为：
> ① 核对「技术方案」门控并记录：`stage check --version v1.0.0 --stage tech --check "三份技术文档已完成|ok|tech-solution、api-design、db-design 均无占位符|manual" --check "核心实现路径都有结论|ok|2 条均已实测通过|manual" …`
> ② 使用者已看过这些摘要并明确同意 → `stage complete --version v1.0.0 --stage tech --signer lisi --quote "没问题，往下走吧" --by ai`
> ③ `stage enter --version v1.0.0 --stage test_design --by ai`
> ④ 提交并推送，接着执行 SOP-03 A 编写测试计划与用例
>
> ❌ 错误行为：直接进入「开发中」，测试计划和用例留到开发期间或开发后再写（命令也会拒绝）

**反例：**
> ❌ 在版本 README 或别的文档里手写「技术方案 ✅」，没有运行命令
> ❌ `--quote` 填「使用者同意」这类转述，不是原话
> ❌ 使用者没看摘要就替他记签收

**示例：阶段回退（测试发现严重问题，需要回到开发阶段）**
> 用户说：「测试发现 P0 缺陷 BUG-xiaozhou-003，需要回到开发阶段修复」
>
> AI 正确行为：
> ① `stage rollback --version v1.0.0 --from test --to dev --reason "发现 P0 缺陷 BUG-xiaozhou-003" --ref BUG-xiaozhou-003 --quote "需要回到开发阶段修复" --by ai`
> 　 `--quote` 填使用者决定回退的那句话；使用者只是报告了问题、还没说要回退时，先问清再记
> ② 回退后当前阶段就是「开发中」，不用再运行 `stage enter`；「开发中」和「测试」之前的签收都失效，修复后要重新核对门控、重新签收
> ③ 提交并推送
>
> **从发布回退**（生产业务验证或生产验收发现缺陷，如 BUG-xiaozhou-005）：`stage rollback --from release --to dev`，原因写明缺陷编号；已回滚的另用 `deploy --action rollback` 记录，没回滚的不用记，`status` 会照实显示线上在跑的版本。修复后重新走开发、测试、发布的门控和签收
>
> ❌ 错误行为：仅在 defects.md 记录缺陷，不记录阶段回退
