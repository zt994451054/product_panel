# SOP-06 新建迭代版本

**触发**：需要开始新的迭代版本。上一个版本不必已发布：多个版本可以同时推进，地位相同，没有「主线版本」；挂起、恢复或放弃一个未发布的版本也按本 SOP

**版本号语义：**
- major（v1→v2）：产品重大转向或破坏性改动
- minor（v1.0→v1.1）：完整功能迭代（常规版本）
- patch（v1.0.0→v1.0.1）：Bug 修复、小调整

**步骤：**
1. 与用户确认新版本号、版本目标（一句话；使用者暂时说不出就先不填，之后补）、产品 / 研发 / 测试负责人、计划发布日（可以先不定）
2. 先 `git fetch --all`，再运行 `version new` 登记版本（命令见 [state.md](../state.md)）。命令会在本机能看到的所有分支上检查版本号有没有被占用，被占用就换一个号，不需要先合入哪条分支。没拉取就看不到别人刚占的号。先登记再建目录：命令被拒绝时不会留下一个没登记的目录
3. 在 `versions/` 下新建 `{新版本号}/` 目录，复制 v1.0.0/ 完整结构（不复制 `state/`）
4. 清空各子文档正文内容，保留模板占位结构。上一版本的测试结果、豁免、决策、待验证假设都不继承：仍要遵守的决定和仍未解决的豁免项，在新版本里重新登记并由使用者重新确认
5. 若新版本已在 `versions/README.md`「版本规划（近期）」表中，将其从规划表中删除（已立项，不再是规划中）
6. 还有其他未发布的版本时，提醒使用者：之后操作要指明版本号；本版本和它们改同一模块、表或配置的，发布顺序和合并方式由使用者决定
7. 立即提交并推送，其他人才能看到这个版本号已被占用。推送不了时告诉使用者：这个版本号目前只有本机知道，别人可能用掉同一个号

**完成标志**：新版本目录已创建，`status` 里能看到新版本（规划中）

**挂起、恢复与放弃**：版本暂停推进用 `version hold`（写明原因、什么条件下恢复），恢复用 `version resume`，决定不再做用 `version abandon`。三者都只由使用者决定，`--quote` 填原话。挂起期间不计入阶段天数和停滞预警；挂起或放弃的版本不能再推进阶段。版本目录保留，不删除。

**示例：v1.0.0 还在测试，并行启动 v1.1.0**
> 用户说：「v1.0.0 还在测，先把 v1.1.0 立起来，做预约改期，负责人还是我们三个」
>
> AI 正确行为：
> ① 确认新版本号为 v1.1.0（功能迭代 → minor 版本）、目标、负责人
> ③ 复制 versions/v1.0.0/ 的目录结构到 versions/v1.1.0/，清空以下文件正文内容（保留模板占位结构和注释）：
>    product/requirements.md / design-spec.md
>    engineering/tech-solution.md / api-design.md / db-design.md / release.md
>    testing/test-plan.md / test-cases.md / defects.md / test-report.md
>    CHANGES.md（清空变更汇总表和变更详情，注释模板保留）、decisions.md（清空表格行）
>    README.md（清空版本背景 / 目标 / 范围 / 交接）
> ② `version new --version v1.1.0 --goal "支持预约改期" --product xiaolin --engineering azhe --testing zhouzhou --by xiaolin`
> ④ 告知：「现在有两个未发布的版本，之后请说明要操作哪一个」
> ⑤ 提交并推送
>
> ❌ 错误行为：只建目录、不运行命令（状态里没有这个版本，别人可能用掉同一个版本号）
> ❌ 错误行为：命令提示版本号已被占用时，手写事件文件绕过
