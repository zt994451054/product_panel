# SOP-09.5 只读探索与回填

**触发**：配置项选了 🔍 探索，或任何需要从代码、文档、线上系统整理现状写入面板的工作

**流程**：使用者给线索 → AI 只读探查 → 草稿写入目标文件 → 回报 → 使用者审批 → 生效

**规则：**
1. **只读**：不修改被探索的工程和系统；只运行读取类命令，不部署、不迁移、不改配置、不发写请求。需要访问线上系统时，先问使用者怎么访问
2. **写明来源**：每条事实带证据（文件路径和行号、命令及关键输出、或「@xx 口述」）。没有证据的不算事实
3. **事实和推断分开**：推断写「推断：…（依据：…）」。查不到的写「待确认」，不补全、不猜
4. **矛盾不替使用者选**：文档和配置、配置和实际不一致时，两边都写出来，列为待确认问题。例如文档写 pm2、CI 配置是 docker，不能择一写入
5. **草稿直接写入目标文件**，顶部加横幅，状态表改为 📝：
   ```markdown
   > 🤖 AI 草稿待审｜来源：{路径或线索}｜待确认：{问题，或「无」}
   ```
   模板里与实际不符的示例内容要删掉或改写，不留在草稿里
6. **只有使用者能确认**：使用者看过摘要并明确同意后，去掉横幅、状态改为 ✅。可以按项也可以按批确认。「你看着办」「先这样」不算确认
7. **回报**：先说结论，再列矛盾和待确认问题，一轮最多问 4 个，其余放进文件的待确认列表
8. **物料**：使用者提供的资料放 `materials/`（不入 git），在 `materials/README.md` 登记来源和提炼去向
9. **大范围探索**可以派子 agent 分头读，主 agent 汇总。子 agent 同样只读，只把结论和证据交回来，由主 agent 写入面板。工具不支持子 agent 时自己做
10. **凭据**：探索中遇到的凭据按使用者意愿处理，写入值或只写位置都可以

**示例：**
> 使用者说：「生产怎么部署的我也不太确定，你按看到的写吧。」
>
> AI 正确行为：
> ① 只读查看部署文档、CI 配置、Dockerfile
> ② 写入 `engineering/docs/ops-profile.md`，加横幅，部署方式写「待确认：`docs/deploy.md:12` 写 pm2，`.github/workflows/deploy.yml:30` 是 docker push」
> ③ 回报：「部署方式有矛盾，文档说 pm2，CI 是 docker。线上实际是哪种？你不确定的话，能不能问问运维，或者给我一个能看的入口？」
>
> ❌ 错误行为：按「看到的」写成 docker 部署，不标待确认
> ❌ 错误行为：为了确认部署方式去改配置或重新部署
